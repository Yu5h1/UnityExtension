## 設計決策

### 1. 泡泡樣式:三段式,先做最簡單那段
三種模式:**統一樣式**(全體共用一套)→ **我方/其他人**(兩套)→ **每人自訂**(每個參與者自己一套)。最終形態預設走「每人自訂」,但本輪只做「統一樣式」。
**約束**:參與者/使用者資料結構現在就要預留樣式欄位(例如 `Participant.BubbleStyle`),即使 v1 不讀它,避免將來升級到「每人自訂」時是一次破壞性改資料結構的動作。

### 2. 顏色來源:改成使用者資料驅動,不搬天空自適應演算法
HealthAI 現行的 `ImmersiveTextController`/`SkyTextContrast` 是「每幀依日夜天空色即時算對比度」的動態演算法,綁死在 HealthAI 自己的日夜天空系統上。**通用模組不搬這個演算法**,改成顏色是使用者資料的一部分,套用哪一套跟決策 1 同一套模式(統一/我方他人/每人自訂)。
`BubbleStyle` 不只是顏色,還涵蓋形狀、背景貼圖——即顏色/形狀/背景圖三種表現方式都要能設定。

### 3. 頭像:可關閉,沒提供時用預設向量圖示占位
頭像功能整體有 config 開關。有開啟但個別使用者沒提供頭像時,顯示一個**預設向量圖示**(非文字占位符),由套件內建生成。

### 4. 名稱顯示:三態,依聊天室類型自適應
設定值:**自適應 / 一律顯示 / 不顯示自己**。「不顯示自己」= 自己的訊息不顯示名稱,其他人的訊息仍顯示名稱(不是雙方都不顯示)。「自適應」預設邏輯:兩人聊天不顯示名稱,多人聊天顯示名稱(或依 config 覆寫)。

### 5. 對齊:預設全部靠左,一個 toggle 決定「自己」是否靠右
不做「多方各自左右」的複雜規則——**只有「自己」的訊息受一個 toggle 控制**(靠左/靠右),其餘所有參與者一律靠左,不管參與者有幾方。理由:全球 UX 慣例是由左至右閱讀,聊天軟體讓使用者自己的訊息靠右是常見慣例,文字書寫方向本身不受影響。

### 6. 時間戳記:統一成單一 config 開關
HealthAI 現況是「即時畫面完全沒有時間戳記,只有另一個歷史 transcript sheet 才有日期分隔線+每則時間」,兩套邏輯分開維護。**通用模組統一成一個 config 開關**,控制同一個聊天面板要不要顯示時間/日期分隔,不再區分「即時」與「歷史」兩種畫面各自一套。

### 7. 串流介面:統一走累積快照(cumulative snapshot),不支援差量
呼叫端一律透過同一個 API 餵內容進來;來源若非串流(一次到位),模組不等待、直接顯示,不需要另一套非串流專用介面。
**資料形狀定案為累積快照**(每次回呼帶「目前為止的完整文字」,而非「這次新增的片段」)。理由:HealthAI 現有的原生橋接(Swift `streamResponse` → Unity)本來就是傳累積全文快照,選累積快照可以讓未來 HealthAI 真的接上這個模組時,原生端完全不用改,只有差量介面才會逼著回頭改 Swift 程式碼。

### 8. 思考中指示器:隨模組抽出,由串流狀態機自然驅動
不是獨立可關閉的功能——只要走同一套統一串流介面,「思考中」狀態就是「尚未收到第一批內容」這個狀態的自然呈現;內容瞬間到位時,思考中狀態長度自然為零,不需要額外開關去跳過它。

### 9. 捲動跟隨 + 依距離淡出:兩者都算聊天面板本體行為
HealthAI 現行「串流時自動跟到底部、使用者手動上滑就停止跟隨」與「離螢幕中心越遠透明度越低」兩個行為,**都收進聊天面板模組**,不排除淡出效果當作 HealthAI 專屬的美術裝飾。
(淡出後來改成單向、可關閉,見下方「淡出改成單向,可關閉」。)

### 10. Composer(含麥克風)一併搬進 `uitoolkit`
Composer(輸入框 + 送出 + 麥克風)整體搬進 `yu5h1lib.uitoolkit`,不是只搬訊息列表。

### 11. `reduceMotion` 由 `animation` 套件負責
依賴方向已定案:`uitoolkit → animation → common`(見主計畫[系統階層與關係](file:///W:/UnityProject/HealthAI/docs/unity/套件解耦計畫.md#系統階層與關係))。聊天面板模組（`uitoolkit`）的串流揭露、捲動動畫等直接沿用 `animation` 既有的 reduceMotion 機制，不另外自己實作一套。

## 開發方式

- Demo（`ChatModuleDemo.cs` + 場景）暫時放在 `Packages/UIToolkit/_dev/ChatModule/`（不是 `Samples~`），
  這樣 `Yu5h1LibTest` 靠既有的 `file:` 路徑引用就能直接編譯、即時看到變更，不用每次改動都手動複製進
  `Assets/`。整個模組完成、穩定後，最後一次把 `_dev/ChatModule` 搬進 `Samples~/ChatModule/` 正式出貨。
- 模組本體程式碼直接寫在 `Packages/UIToolkit/Runtime/Chat/`（永久位置，不是暫存）。

### Enter 送出(推翻先前決策)
之前(決策 10)照 HealthAI 的作法完全不讓 Enter 送出,避免跟輸入法選字衝突。這次使用者明確要求
**Enter 必須送出**——現在幾乎所有聊天 app 都這樣做,衝突的正確解法不是「乾脆不用 Enter」,是**只在
IME 真的在組字的時候放行**。`ChatComposer` 新增 `KeyDownEvent` 處理(`TrickleDown`,搶在輸入框自己
處理之前):`UnityEngine.Input.compositionString` 非空就直接 return,交給 IME;否則呼叫同一個
`Submit()`(跟按送出鈕共用)。**用真的 `KeyDownEvent.GetPooled(...)` 透過 `SendEvent` 丟進活的
Play Mode panel 實測過**:設定草稿文字、送出模擬 Enter,訊息列表確實多一筆、草稿確實清空——不是只看
程式碼推論。IME 組字中會不會正確放行,因為沒辦法用程式模擬真正的 IME 狀態,**這部分只驗證到邏輯正確
(`compositionString` 非空就 return),沒有互動實測**。

### Composer 改成膠囊狀,麥克風+送出都在裡面靠右
`ChatComposer.Root` 現在是**單一個膠囊容器**(高度 52、圓角 26,數字照抄 HealthAI `.composer`/`.send`
的尺寸),`TextField`(`flex-grow:1`)+ 麥克風 + 送出鈕全部塞在同一個膠囊裡,`flex-grow` 自然把兩顆
按鈕推到最右邊。跟 HealthAI 原本「膠囊(文字框+麥克風)+ 外面一顆獨立圓形送出鈕」的兩件式作法不同——
這是使用者要求的簡化版,比較接近 iMessage/Telegram 那種「全部塞一個膠囊」的現代樣式。送出鈕用
`SetEnabled` 控制,Unity 內建的 `:disabled` 虛擬狀態(resolvedStyle.opacity 0.5)已經直接給出「停用時
變暗」的效果,不用自己再刻一份變色邏輯。

### 聊天室由下往上疊加(踩到一個 Yoga 版面引擎 bug)
HealthAI 的 `.messages { justify-content: flex-end; }` 這招(短對話貼齊底部,不是飄在頂端留一堆空白)
**直接照搬到 `ScrollView` 的 `contentContainer` 上會壞**——實測發現這個版本的 Unity,
`justify-content:flex-end` 只要跟「子元素內容比容器本身還高」同時出現,容器的版面高度就會被鎖死在
`min-height`(或完全不設時鎖在某個小值),超出的子元素全部被推到負座標、滾到畫面外,`ScrollView` 自己
算可捲動範圍用的也是這個錯的高度,整個捲動跟著壞掉。換成在**另一個子元素**(`stack`,本身不是
`contentContainer`)上設一樣的 `justify-content` 也一樣壞,換成絕對像素 `min-height`(不用
`Length.Percent(100)`)還是壞——用 `Debug.Log` 把 `stack.layout`/`children[].worldBound` 真的印出來,
才確認是容器高度被鎖死,不是我原本猜的百分比解析問題。
**最後改用算出來的 `marginTop`**:`ChatPresenter.Tick()` 每幀比較 `stack` 跟 viewport 的高度,不夠高
就補一個 `marginTop` 把內容推到底部,完全不碰 `justify-content`——這個路徑通過了全部 12 個 PlayMode
測試(含原本的 `ChatPresenterScrollTests`),包括重新截圖確認視覺效果正確(三則不同長度的訊息確實貼齊
底部,上方留白)。

### 隱藏式(hover 淡入)捲軸
照抄 HealthAI `.app .unity-scroller--vertical` 那整組 USS 規則,但因為套件元件不該要求呼叫端一定要
載入某份 USS,改成直接在 `ChatPresenter` 建構子裡用 C# 設定同樣的樣式(反射確認過
`ScrollView.verticalScroller`/`Scroller.lowButton`/`.slider`/`Slider.trackerUssClassName` 等欄位、
常數都是 public,不用猜字串):捲軸絕對定位、寬度 12px、預設 `opacity:0`,`MouseEnterEvent`/
`MouseLeaveEvent`(不是 `PointerEnterEvent`——UI Toolkit 裡 Pointer 版本不會對整個子樹冒泡,Mouse
版本才會,這點容易選錯)切換到 1,搭配 180ms 的 `transitionDuration`。上下按鈕隱藏、滑塊改成 4px 圓角
細長條。

### Demo:可編輯的測試資料池
`ChatModuleDemo` 新增兩個可在 Inspector 直接改的欄位:
- `simulatedReplies`(`string[]`):模擬回覆的文字池,預設給短/中/長三種長度,每次回覆隨機抽一則,
  用來確認泡泡在不同長度下的換行、圓角、最大寬度效果。
- `thinkingTimePool`(`float[]`):思考秒數池,預設 `{0, 6}`,每次隨機抽一個——0 秒驗證「不是串流就
  直接顯示、思考中自然跳過」那條路徑,6 秒驗證點點循環 + 超過 5 秒附加秒數的那條路徑。

初始訊息列表也改成直接塞短/中/長三則(不用再手動打字才看得到長訊息的樣子)。另外比照 HealthAI `.app`
加上 430px 的寬度上限——當時直接設在根元素上,實際**沒有置中**,第二輪改成另包一層 wrapper,見下方
「視覺修正與裝置適配」。

### 驗證總結
EditMode 107/107、PlayMode 12/12 全過(含上面提到的捲動迴歸修正);Enter 送出用真實
`KeyDownEvent` 經 `SendEvent` 實測通過;膠囊 composer、三則不同長度訊息貼底、隱藏式捲軸均以 Play Mode
截圖確認。IME 組字中按 Enter 的放行邏輯**只做到程式碼正確,沒有實機 IME 操作驗證**。

## 視覺修正與裝置適配(2026-10-01,第二輪)

使用者實際看 demo(含 Device Simulator)後逐項回報的問題。每一項都先用 `resolvedStyle`/`worldBound`
量出實際數值找到根因才改,不是憑截圖猜。

### 置中:UIDocument 的 root 本身不能拿來置中
`UIDocument.rootVisualElement` 內建 `position:absolute; left:0; right:0`(用來填滿 panel)。在它身上
設 `width`/`max-width`/`align-self` 時,寬度確實被 `max-width` 夾到 430,但 `left:0` 把它釘在最左邊,
`align-self` 完全不生效。改法:root 維持預設的滿版行為,改成 `flex-direction:row; justify-content:center`,
430 欄位放在另一層一般 flex 子元素(`chat-module-demo-frame`)上。

### 頁面背景必須自己畫
root 跟 frame 原本完全透明。Editor Game View 的預設清除色剛好是深灰,把這個破洞蓋住了;Device Simulator
的清除色不同,上半部的空白區就露出淺灰。Demo 現在在 root 上明確畫 `PageBackground`。**套件本身
(`ChatPresenter`)刻意不畫頁面背景**——頁面背景是使用端 app 的事,元件不該替整個畫面決定底色。

### 泡泡文字顏色:`BubbleStyle.TextColor`(新欄位)
`BubbleStyle` 原本只有背景色、圓角、背景圖,沒有文字顏色,訊息文字只能吃到主題預設值(偏暗),在深藍
泡泡上幾乎看不清。新增 `TextColor`(預設白色——實心底色泡泡上的通用慣例),由 `ApplyStyle` 設在泡泡容器
上,名稱/內文/時間戳記三個 Label 靠 `color` 繼承拿到,不用各自知道 `BubbleStyle`。

### 主題的 Label 預設間距
`ChatModuleTheme.tss` 的 Label 基底樣式會在每一邊加 margin/padding。實測名稱 Label 吃到 margin-top 4、
padding 上下各 4、margin-bottom 2,內文又多 margin-top 4——第一行字開始前就堆了 31px。`ChatPresenter`
新增 `ZeroSpacing()` 把名稱/內文/時間戳記的 margin、padding 歸零,只保留一個刻意設的名稱下方 2px。
泡泡內的間距由 `ChatPresenter` 決定,不是交給某條通用主題規則。

### 頭像對齊泡泡頂部
訊息列原本 `align-items:flex-end`,多行訊息時頭像被壓到泡泡底部。改成 `flex-start`,頭像對齊泡泡頂角,
跟主流聊天 app 一致。

### 淡出改成單向,可關閉
原本照 HealthAI 以 viewport 中心為準、上下對稱變淡。使用者要求漸層方向跟著訊息疊加方向走:訊息由下往上疊,
所以**最底下(最新)完全不透明,往上(越舊)越透明**,到 viewport 頂端是 `MinRowOpacity`(0.35)。量的是列的
下緣加上 `marginBottom`,所以貼在底部的最新一則剛好是 1。新增 `ChatModuleConfig.FadeMessages`(預設開),
`ChatPresenter` 每幀讀,可以執行中切換;關掉時用 `StyleKeyword.Null` 清掉 opacity。Demo 的 Inspector 有
`fadeMessages` 開關對應它。

### 隱藏式捲軸的白線
捲軸內的 `#unity-tracker` 主題預設有 1px 灰色**右**邊框(先前只清了左邊框),而主題把 slider 撐到 24px 寬,
超出 12px 的捲軸容器,所以那條線畫在捲軸外面。改成 tracker 四邊邊框全清、slider 寬度 100%、捲軸容器
`overflow:hidden`。

### Composer:文字對比、placeholder、向量圖示
- **文字顏色**:膠囊底色固定是淺灰,輸入文字若吃到宿主主題的淺色預設值就會看不見,所以明確設成深色。
- **Placeholder**:Unity 6000.6.0f1 的 `TextField` 反射確認**沒有公開的 placeholder API**。改成一個疊在
  輸入框內層(`.unity-base-text-field__input`)上的 `Label`,`position:absolute` 對齊同一個 padding box、
  `pickingMode:Ignore` 讓點擊穿透,`Draft` 有內容時隱藏。文字「想說什麼?」、黑色 66.6% 透明度,以
  `ChatComposer.Placeholder` 公開讓使用端改字或改樣式。`ClearDraft()` 用的 `SetValueWithoutNotify` 不會
  觸發 value-changed,所以它要自己更新 placeholder 顯示狀態。
- **向量圖示**:🎤 在預設字型裡沒有字符,會畫成方塊(tofu)。麥克風(膠囊 + 支架 + 底座,錄音時換成紅點)
  與送出鈕(向上三角形)都改用 `generateVisualContent` + `Painter2D` 繪製,`Recording` 變更時
  `MarkDirtyRepaint()`。圓角用 `ArcTo`、支架曲線用 `QuadraticCurveTo`,刻意不用 `Arc`——`Arc` 需要角度
  與方向慣例,`ArcTo` 只靠座標。**這只是兩個圖示的就地繪製,不是 [向量圖示系統.md](向量圖示系統.md) 那個
  通用、可主題化的子系統**,範疇切割不變。

### Demo 頭像:程式化繪製
`generate_image` 的兩個供應商(fal.ai、OpenRouter)在這個專案都沒設定 API Key,使用者選擇先用程式畫簡易版。
`_dev/ChatModule/ProceduralAvatarGenerator.cs` 用圓/橢圓/線段直接寫進 `Texture2D`(塗鴉風使用者、美少女
AI)。注意 `Texture2D.SetPixels` 的緩衝區是**由下往上**(第 0 列是最底下),而形狀座標是由上往下寫的,
所以在唯一寫像素的 `SetPixelSafe` 裡翻轉 y。這是 demo 的測試資料,不屬於套件。

### 裝置適配:`DevicePanel`(套件 helper)
Device Simulator(1170×2532 @460dpi)上整個 UI 只佔螢幕約三分之一寬。原因是 `ConstantPixelSize`:
1 UI 單位 = 1 實體像素,430px 在高密度手機上只是很窄一條,字也小到看不清。另外 safe area 上有瀏海、下有
Home 指示條,composer 會壓在指示條底下。

這件事每個使用端都會遇到,所以抽成套件的 `Runtime/Device/DevicePanel.cs`:
- `ApplyScale(PanelSettings)`:改成 `ConstantPhysicalSize`,行動裝置以 160dpi 為 1x(Android dp,接近 iOS
  pt)、桌面以 96dpi 為 1x(桌面 OS 回報的本來就是含系統縮放的邏輯 dpi,所以桌面行為不變)。
- `PadToSafeArea(VisualElement)`:把 safe-area inset 設成該元素的 padding,每次 geometry 變更重算(轉向)。
  用在滿版的 root 上:背景照樣延伸到瀏海底下,只有內容往內縮。會覆寫該元素原有的 padding。
- `SafeAreaInsets(Rect, Vector2, float)`:純函式,把 Unity 螢幕座標(實體像素、**原點在左下**)的
  safe area 換算成 panel 單位的上下左右 inset。上方 inset 要用 `screen.height - yMax` 算,這是最容易寫反的地方。

**一律讀 `UnityEngine.Device.*`,不是 `Application`/`Screen`/`SystemInfo`**:實機上兩者相同,但在 Device
Simulator 裡一般版本仍回報 `WindowsEditor`/`Desktop`,只有 `Device` 版本會被模擬(實測
`UnityEngine.Device.Application.isMobilePlatform == true`、`platform == IPhonePlayer`)。

實測結果(模擬 iPhone 1170×2532 @460dpi):邏輯畫面 407×881(iPhone 12 為 390×844pt,同一級),
safe area 上 49 / 下 35.5(iOS 實際 47pt / 34pt),composer 底部停在 829,指示條區從 845 才開始。

**使用端(例如 HealthAI 第二階段接入)要在自己的 `PanelSettings` 呼叫 `ApplyScale`、在自己的 root 呼叫
`PadToSafeArea`**——套件不擁有使用端的 PanelSettings,不會自動做。

### 泡泡最大寬度在各寬度下的實測
在 Play Mode 暫時覆寫 frame 寬度、呼叫 panel 的 `ValidateLayout()` 強制同步排版後量測
(`bubble = row × 85% − (頭像 32 + 間距 8)`):

| 容器寬 | frame | row | 泡泡 | composer 內容寬 |
|---|---|---|---|---|
| 750(桌面) | 430(上限) | 338 | 298 | 398 |
| 375 | 375 | 291 | 251 | 343 |
| 320 | 320 | 245 | 205 | 288 |

320 寬時麥克風/送出鈕仍維持完整尺寸,輸入框剩 194 可用,沒有溢出。
