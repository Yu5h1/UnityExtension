# 運動系統

> 狀態：已實作（`com.yu5h1.animation`）。tween 引擎抽換層仍在設計中，見
> [Motion_System_Refactor](../.agents/plans/Motion_System_Refactor.md)。
>
> 與其他文件的關係：指標事件、元素驅動與世界橋接見[指標互動與世界橋接](指標互動與世界橋接.md)；
> 執行狀態與下一步留在 [handoff.md](../handoff.md)。

## 系統階層與關係

```text
com.yu5h1.animation
├─ Drive                被運動驅動的對象契約
│  ├─ ITarget           還活著嗎
│  ├─ ISpatial          矩形與透明度
│  └─ IPivot            旋轉、縮放、支點
├─ Reaction             事件驅動：無終點，速度守恆
│  ├─ Spring            可 retarget 的阻尼彈簧
│  ├─ Hanging           有角度上限的擺盪，含力矩換算
│  ├─ Shake             一次性抖動，建立在 Hanging 上
│  └─ Throw             帶阻力的拋體，含邊緣反彈與掃掠命中回呼
└─ Transition           時間驅動：有 duration 與曲線
   ├─ Entrance          單一項目從畫外到定位
   └─ Opening           共用時鐘的整組演出，可跳過

com.yu5h1.uitoolkit → 實作 Drive 的 VisualElement 適配器
```

`animation` 不認識任何 UI 型別。它只寫數字到 `Drive` 的介面上，適配器住在 `uitoolkit`，
依賴方向是 `uitoolkit → animation`，反向不存在。`Reaction` 與 `Transition` 互不依賴。

## 摘要

這個系統負責「值隨時間變化」這件事本身，以及它該寫給誰。運動核心只算數字，
被驅動的對象透過 `Drive` 的介面接進來，所以同一段運動可以驅動 `VisualElement`、
`Transform` 或測試替身。

## 問題與目標

- **問題**：能否中斷、能否接手，是互動式運動與播放式動畫最根本的差別，
  而把兩者放在同一組介面下會讓其中一邊被扭曲。
- **目標**：讓「有沒有終點」成為分類的第一層，兩族各自完整。
- **目標**：運動核心不認識任何 UI 技術。
- **非目標**：不提供 tween 引擎抽換（那屬於 `motion-system` 任務）。

## 責任邊界

| 擁有 | 不擁有 |
|---|---|
| 積分、衰減、曲線約定、時序編排 | 任何 `VisualElement`、`Transform`、`Camera` |
| 被驅動對象的抽象（`Drive`） | 對象實際長什麼樣 |
| 「還活著嗎」的詢問 | 對象消失後該怎麼善後 |

減量動態（reduce motion）由呼叫端判斷後以參數傳入；系統不讀取平台偏好。

## 設計

### 分界：有沒有終點

| | `Transition` | `Reaction` |
|---|---|---|
| 被告知 | 終點與時長 | 只有力或目標 |
| 中斷時 | 等於取消 | 帶著速度轉彎 |
| 典型 | 入場、面板展開 | 彈簧、擺盪、抖動、甩飛 |

`Spring` 在 retarget 時保留位置**與速度**，這是 duration 式補間做不到的：
取消重來會丟掉速度，視覺上一頓。抓住、放開、再抓住能連續，靠的就是這一點。

甩飛看起來像移動，但沒有任何東西決定它停在哪 —— 停在哪是物理的結果 —— 所以它屬於 `Reaction`。

### `Drive` 為何獨立

三個介面描述的是「運動可以碰什麼」，不是「哪種運動在碰」。
`Transition.Entrance` 與 `Reaction.Shake` 都需要目標，若介面掛在其中一族底下，
另一族就得為了取用而依賴它，正好反轉兩族要表達的分界。

介面依「寫什麼」而非「誰來寫」切分：擺盪需要支點不需要矩形，行進需要矩形不需要支點，
一個適配器可以同時實作兩者，通常也會。

### 曲線約定

`Transition.ScaleTrack` 把曲線讀成「正規化形狀 ＋ 末值倍率」兩部分。
讀成絕對尺寸會讓隨機起始值把尺寸推成負數 —— `Lerp(10, 1, 1.2)` 是 `-0.8`，
起始抽得越大越早發生。

### 時序編排

`Entrance.Schedule` 的兩個轉盤是演出的兩端，彼此獨立：
`startInterval` 只把起飛拉開，`endTogether` 只把降落收攏。一起降落不代表一起起飛，
錯開起飛只是讓後面的項目飛得快一些。

間隔會在放不下時壓縮，否則多加一個項目就會把最後幾個的起飛推過演出結尾，
讓它們以負的時間長度飛行，而且不會有任何錯誤訊息。

## 案例

- **可中斷的面板開合**：`Reaction.Spring` 從 1（關）到 0（開）。連續點擊不會跳動，
  因為第二次點擊承接的是當下的位置與速度。
- **接住掉落物**：`Reaction.Shake` 建立在 `Hanging` 上 —— 入場擺盪與接住是同一件事，
  一次衝量衰減回靜止，差別只在力道與支點。
- **開場演出**：`Transition.Opening` 持有多個 `Entrance` 與一個共用時鐘，隨時可跳過。
- **甩出圖示**：`Reaction.Throw` 帶阻力滑行、撞邊界反彈、命中一次後彈開、壽命到就靜止。

## 決策理由與替代方案

- **容器命名為 `Transition` 而非 `Motion`**：`UnityEngine.Motion` 是既有型別
  （`AnimationClip` 與 `BlendTree` 的基底），掛在 `Yu5h1Lib` 這一層會在整個 library 遮蔽它，
  而 animation 套件正是最可能需要它的地方。`UnityEngine.Animation` 同理，
  所以 namespace 採扁平的 `Yu5h1Lib`。
- **`Entrance` 不實作 tween 殼的 handle 介面**：那個介面是
  `Play`／`PlayBackwards`／`Pause`／`Stop`／`Rewind` 加單一型別的起訖值，由引擎 runner 驅動；
  入場是共用時鐘、各自窗口、三值姿態，且不使用任何 tween 引擎。硬套買不到抽換能力，
  卻會在 `motion-system` 的核心契約定案前，先用一個它不服務的案例去塑形它。
- **已排除：依賴多寡決定歸屬。** 彈簧沒有 Unity 依賴，照那個標準會被放進 `common`，
  但它就是動畫核心。歸屬看概念，依賴檢查只用來驗證去處可行。
