# 非同步工作：事件設計與工作物件

> Task ID: async-task

狀態：設計中（2026-10-21）。程式在 `com.yu5h1.common`，不只給網路或資源讀取用。
待決題：[async-task.decisions](../decisions/async-task.decisions)。

## 為什麼需要

- 流式下載的 UX 需要非同步處理，讀取資源還要回報進度（字節完成度）。第一個消費端是
  [Addressables 套件](Addressables/plan.md) 的讀取處理器。
- VCP 的 ChatRequest 已經有一套實際在跑的設計：`RequestData`（inline SO）＋`TaskEvent<string>`。
  它用 `IEnumerator`／`yield return`，而且綁著 VCP 的協定。
- `LoadSceneAsync`、Timer 這類不是網路的工作，也需要同一套事件驅動畫面。

## 已決定（2026-10-21）

- **`AsyncTaskObject` 以 `RequestData` 為藍本**（它本來就是），把 `IEnumerator`／`yield return` 換成 `Awaitable`。
  它只處理請求與結果判斷。
- **`AsyncProgressObject : AsyncTaskObject`** 多一個 `Progress<float>`，例如讀取資源時依字節範圍與完成度回報。
  不限網路：`LoadSceneAsync`、Timer 也用它。
- **事件順序**：
  ```text
  Begin → End → 結果判斷 → True／False → Completed
  ```
  - End 之後的結果判斷分成 True／False 兩個分支事件，分支可選用，不必另寫邏輯元件；缺點是事件分開。
  - Completed 不論結果都觸發，放在結果之後，帶 bool（成敗）（決策 `completed-event`）。使用者覺得帶 string 可能更好，
    之後用實際 demo 再判斷。
  - 工作被取消時不觸發結果，只觸發收尾（決策 `cancel-outcome`）。
  - 事件帶什麼參數有衝突，見 [衝突：事件參數](#衝突事件參數)。
- **`TaskEvent` 最終改成這套事件設計**，`AsyncTaskObject` 零散的 UnityEvent 收進 `TaskEvent`。時機依決策
  `taskevent-migration`：`TaskEvent` 先不動，等 ChatRequest 抽成 Network 套件時一起遷移；在那之前新設計只用在
  `AsyncTaskObject`。

## 衝突：事件參數

- 決策頁（2026-10-21 21:08，`event-params`）選「基底不帶參數，結果放屬性」。
- 之後的對話（同日）說請求本身只需要 `Begin<string>`、`End<string>`，結果判斷由 End 的 string 驅動。

兩者不一致，等使用者確認。對照現況：VCP 現有的 `TaskEvent<string>` 正是 Begin、End、True、False 帶 string，Completed 帶 bool；
對話裡的設計和它幾乎一樣，差在多了進度，以及下面待分析的結果判斷物件。
- **非同步處理器先不做替換能力**，只用 `Awaitable`。留的路：`Awaitable` 只出現在處理器與工作物件的程式內部，
  不進入序列化欄位、也不進入 UnityEvent 的簽章；場景一側的契約一律是事件。之後真的要換成 UniTask，
  只需要換處理器內部，再考慮包成可替換的殼。

## 待分析：結果判斷改成可組裝的邏輯事件物件

使用者 2026-10-21 的假說：請求本身只需要 `Begin<string>`、`End<string>`；結果判斷是一個邏輯事件物件，
由 End 叫用並傳入 string，判斷邏輯由消費端定義。觸發方式可選：要直接執行就用一般事件物件，要非同步就用非同步事件物件。
Completed 在結果判斷之後。

決定之前要先深度分析：

- **ChatRequest 的處理設計理由**：`RequestData.Complete` 的判斷順序（HTTP 結果 → `vcpMessage` 解析 → `IsException`
  → 錯誤碼 103 重新登入）、`HandleMessage` 與 `useRawMessage`、`ChatRequest._sharedCallbacks`、串流類別覆寫的 `Processing`。
- **第二階段驗證**：請求結束後再驗證才產生結果（common 已註解的 `WebRequestEvent.Finish<T>(result)`、VCP 留下沒用的
  `vcpFinishRoutine` 別名），怎麼落在結果判斷物件上。
- **`TaskEvent` 現在被引用的情境**：
  - VCP `RequestData`。ChatScene 2026-10-21 的監聽器分布：Begin 14 筆，End 0 筆，Completed 6 筆，
    全部是 Inspector 寫死的參數（關 Loading、重新開放送出按鈕等）。
  - UI 套件的 `PopupPanel`（`_callbacks.Invoke(result, result.Content)`）。

## 遷移

`TaskEvent` 改設計會影響已經序列化的監聽器：VCP 場景的 Completed 6 筆要保留，PopupPanel 的用法要對齊。
遷移時機是 ChatRequest 抽成 Network 套件時，方式在上面的分析完成後再定。同一個請求物件重送時，現在的
`StartCoroutine(ref)` 會直接停掉前一個協程，不觸發任何結果或收尾事件；換成 `Awaitable` 後，被取代的請求視為取消，
依 `cancel-outcome` 只觸發收尾，所以 Begin 打開的 Loading 會由收尾關掉。
