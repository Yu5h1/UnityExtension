# 非同步工作：事件設計與工作物件

> Task ID: async-task

狀態：設計已定，待實作（2026-10-22）。先做 [首輪範圍](#首輪讀取角色)，其餘留到 [ChatRequest 優化](#之後chatrequest-優化)。程式在 `com.yu5h1.common`，不只給網路或資源讀取用。
決策檔：[async-task.decisions](../decisions/async-task.decisions)。

## 為什麼需要

- 流式下載的 UX 需要非同步處理，讀取資源還要回報進度（字節完成度）。第一個消費端是
  [Addressables 套件](Addressables/plan.md) 的讀取處理器。
- VCP 的 ChatRequest 已經有一套實際在跑的設計：`RequestData`（inline SO）＋`TaskEvent<string>`。
  它用 `IEnumerator`／`yield return`，而且綁著 VCP 的協定。
- `LoadSceneAsync`、Timer 這類不是網路的工作，也需要同一套事件驅動畫面。

## 已決定

- **`AsyncTaskObject` 以 `RequestData` 為藍本**（它本來就是），把 `IEnumerator`／`yield return` 換成 `Awaitable`。
  它只處理工作本身。
- **`AsyncProgressObject : AsyncTaskObject`** 多一個 `Progress<float>`，例如讀取資源時依字節範圍與完成度回報。
  不限網路：`LoadSceneAsync`、Timer 也用它。
- **事件順序**：
  ```text
  Begin<string> → [Progress<float>] → End<string> → 判斷物件（await）→ True<string>／False<string> → Completed<bool>
  ```
- **工作物件只固定 Begin、End**，都帶 string（決策 `event-params`，2026-10-22 以對話為準）。End 帶完整的回應內容，
  作為判斷物件的輸入；例如 HTTP 回應全文，串流就是收到的全部內容。
- **判斷物件**：從 PopupPanel `LogicObject` 抽出判斷的部分（`GetResult`），放在 common。
  - 輸入 string，輸出成敗與內容；可以同步，也可以非同步（非同步的用來做第二階段驗證）。
  - 消費端繼承寫自己的變體，例如 VCP 的 `vcpMessage` 判斷（代碼 100～200 是失敗，103 時重新登入）。
    `RequestData`（遷移後）與 PopupPanel 共用同一套判斷物件，`VerificationRequestLogic` 不再自己解析。
  - 判斷物件自帶 True<string>／False<string>／Completed<bool>，用到才加，不在工作物件上固定宣告。
  - True／False 帶 string（內容）：ChatScene 現有 9 筆動態監聽器都讀 string，接收端靠它顯示訊息或解析物件。
- **工作物件有選用的判斷欄位**（決策 `completed-event`，2026-10-22）。工作物件在 End 之後 await 欄位裡的判斷物件、
  存下成敗，再觸發判斷物件的事件。全域錯誤顯示、讀取處理器失敗時改用測試角色這類共用程式，透過欄位讀到成敗；
  沒掛判斷物件就沒有結果事件。
  不由 End 的 UnityEvent 呼叫判斷物件：那樣連結只存在 Inspector 的接線裡，程式找不到請求掛的是哪個判斷物件，
  共用程式拿不到成敗，只能每個請求各接一次，漏接的那個就沒有全域提示。
- **取消**：工作物件不呼叫判斷，觸發 End 與判斷物件的 Completed(false)，不觸發 True／False（決策 `cancel-outcome`）。
  End 負責解鎖、Completed 負責關 Loading，兩個都觸發畫面才會全部還原。
- **讀取結果用型別事件交出，End 不做複合型別**（2026-10-22）。End 維持 string：讀取資源帶 key 或路徑，
  `LoadSceneAsync` 帶場景名，Timer 可留空。結果的型別由子類別決定，例如 `AsyncLoadObject<T> : AsyncProgressObject`
  （T 是 GameObject、AudioClip、Texture 等）：成功時以 `Loaded<T>` 交出物件，同時放在 `Result` 屬性；預設判斷是讀到物件就算成功。
  不把 End 做成「string＋媒體＋物件」的複合型別：UnityEvent 的動態參數要和接收方法同型別，複合型別沒有現成方法接得住，
  每個接收端都要另寫轉接。
- **Completed 帶 bool**。使用者覺得帶 string 可能更好，之後用實際 demo 再判斷。
- **`TaskEvent` 最終改成這套事件設計**。時機依決策 `taskevent-migration`：`TaskEvent` 先不動，等 ChatRequest
  抽成 Network 套件時一起遷移；在那之前新設計只用在 `AsyncTaskObject`。遷移時，VCP 各請求的 True／False／Completed
  監聽器搬到各自的判斷物件上。
- **非同步處理器先不做替換能力**，只用 `Awaitable`。留的路：`Awaitable` 只出現在處理器與工作物件的程式內部，
  不進入序列化欄位、也不進入 UnityEvent 的簽章；場景一側的契約一律是事件。之後真的要換成 UniTask，
  只需要換處理器內部，再考慮包成可替換的殼。

判斷物件的設計來自使用者 2026-10-21 的假說（結果判斷是由 End 的內容驅動、消費端可自訂的邏輯物件），
下一節的分析證實了它。

## 實作範圍

2026-10-22 定：目標是非同步讀取角色，先只做讀取角色用得到的部分。上面〈已決定〉的設計全部保留，分兩段實作。

- `AsyncTaskObject`（`Awaitable`）與 `AsyncProgressObject`：Begin<string>、Progress<float>、End<string>、取消時觸發

### 之後：ChatRequest 優化

ChatRequest 確實需要優化（使用者 2026-10-22）。2026-10-21～22 的討論與分析就是它的設計，在 ChatRequest 抽成

- 第二階段驗證（非同步判斷）在這時才有第一個實際用途。

## 分析結果（2026-10-22）

### ChatRequest 的流程與設計理由

`ChatRequest.BuidlApiRequestPorcess` 的順序：

1. 全域 Begin → 請求的 `Begin()` → `callbacks.Begin("[指令] Begin...
url")`。
2. `Processing`：子類別覆寫。串流類別（`SteamingReadLineRequestData` 以下）在這裡邊下載邊逐行解析、顯示文字、播放語音並等播完，
   信件會自動捲動。
3. `callbacks.End("[指令] End...")` → 請求的 `End()` → 全域 End。
4. `RequestData.Complete`：傳輸失敗就是失敗，內容是錯誤訊息；傳輸成功就解析 `vcpMessage`，代碼 100～200 是例外，算失敗。
   內容取自 `HandleMessage()`：解析後的 content 或原文，串流類別取最後一句。接著 `callbacks.Invoke(成敗, 內容)`，
   觸發 True／False，再觸發 Completed。代碼 103 時另外送出 `account/login` 重新登入。
5. 全域 `_sharedCallbacks.Invoke(成敗, 內容)`。

從程式推得的設計理由：

- SO 不能跑協程，所以由 MonoBehaviour（`ChatRequest`）執行。`ChatRequest` 同時擁有伺服器網址設定與全域回呼，
  全域回呼負責全域等待畫面與全域錯誤顯示。
- `IRequestInfo` 把步驟切開（Begin／Processing／End／Complete），子類別只覆寫需要的那一步：串流覆寫 `Processing`，
  解析覆寫 `HandleMessage`／`TryParse`，自身狀態覆寫 `Begin`／`End`。
- 表演（文字、語音、捲動）都在 `Processing` 裡，所以 End 代表傳輸與表演都結束；Completed 在結果判斷之後。
- 結果判斷寫死在 `RequestData.Complete`，綁著 `vcpMessage` 協定。PopupPanel 的 `VerificationRequestLogic` 需要同一個判斷，
  只能自己再解析一次 `vcpMessage`。
- 第二階段驗證（common 已註解的 `WebRequestEvent.Finish<T>(result)`、VCP 沒用的 `vcpFinishRoutine` 別名）現在沒有實作；
  PopupPanel 的流程（下面）是目前唯一在跑的形式。

### ChatScene 的監聽器分布

14 個請求物件加上 `ChatRequest` 的全域回呼。這是更正：2026-10-21 寫的「End 0 筆」是錯的，當時的掃描漏掉了 End。
決策檔 `completed-event` 的背景說明也引用了這個錯誤數字；該題的答案不受影響，所以沒有修訂題目。

| 事件 | 筆數（請求＋全域） | 怎麼用 |
|---|---|---|
| Begin | 13＋2 | 全部寫死參數：開等待畫面、鎖換頁與送出、觸發角色表情 |
| End | 5＋2 | 全部寫死參數，和 Begin 成對解鎖、關等待畫面（letter 4、sequential 1、全域 2） |
| True | 18＋0 | 5 筆讀取動態 string：`vcp_MentalHealth.Handle`、`vcp_chat_histroy_handler.Handle`、`JsonFieldBinder.Load` 2 筆、`TextAddon.Show`；其餘是換頁、存檔、再送請求等寫死參數 |
| False | 6＋1 | 4 筆讀取動態 string（顯示錯誤訊息，含全域 1 筆）；其餘寫死參數 |
| Completed | 6＋0 | 全部寫死參數：關 Loading、重新開放送出 |

- Begin、End 的 string 沒有任何監聽器讀取，內容只是除錯訊息。
- True、False 的 string 有 9 筆動態監聽器在讀，都是把內容交給解析器或顯示出來。
- `vcp_AudioClient.unity` 的同一組請求只剩 Begin／End 監聽器，沒有結果與 Completed，是舊資料；
  `RequestData.TransferCompletedData` 就是當時用來搬 `outcome.completed` 的。

### 結果判斷物件已經以兩種形式存在

- **消費端處理器**：True(string) 接到 `vcpMessageHandler` 的子類別（`vcp_MentalHealth`、`vcp_chat_histroy_handler`）
  與 `JsonFieldBinder`，各自解析字串。
- **可替換的判斷物件**：PopupPanel 的 `LogicObject`（inline SO）有 `BuildRoutine`（非同步工作）與 `GetResult`
  （判斷，回傳 `Succeeded` 與 `Content`）。PopupPanel 的流程是 Begin("") → 等 `BuildRoutine` → End("") →
  `GetResult` → logic 自己的 `BinaryEvent<string>` → `_callbacks.Invoke`，正是「End 之後交給判斷物件，再分 True／False」。
  `VerificationRequestLogic` 把 `RequestData` 組進來當非同步工作，但判斷要自己重寫。
- PopupPanel 的 `_callbacks` 在 prefab 與 ChatScene 都沒有監聽器；結果走 logic 的 `_reported`。

### 其他引用

本機 Unity 專案裡只有 VCP 使用 `TaskEvent`；UnityExtension 只有 PopupPanel 引用它。

## 遷移

`TaskEvent` 改設計會影響已經序列化的監聽器：VCP 場景的 Completed 6 筆要保留，PopupPanel 的用法要對齊。
遷移時機是 ChatRequest 抽成 Network 套件時，方式在上面的分析完成後再定。同一個請求物件重送時，現在的
`StartCoroutine(ref)` 會直接停掉前一個協程，不觸發任何結果或收尾事件；換成 `Awaitable` 後，被取代的請求視為取消，
依 `cancel-outcome` 只觸發收尾，所以 Begin 打開的 Loading 會由收尾關掉（收尾指 End 與 Completed，見 [已決定](#已決定)）。
