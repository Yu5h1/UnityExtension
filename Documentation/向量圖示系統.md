# 向量圖示系統(Vector Icon System)

> Task ID: vector-icon-system

## 狀態

**設計進行中,尚未實作。** 原本附在[聊天面板模組.md](聊天面板模組.md)底下討論(當時的步驟 8),
2026-10-01 拆出來變成獨立計畫——這是一個獨立的能力,不是聊天模組的一部分,聊天模組只是第一個提出
需求的消費端(頭像預設圖示、麥克風圖示)。

## 問題

`uitoolkit` 現有的 `SignalGraphic.cs`(HealthAI 原始碼,尚未抽離)用 `Painter2D` 手刻每個圖示的座標與
貝茲曲線,沒有可重用的資料格式,也沒有跟 web 共用素材的路徑。使用者曾用過 `com.unity.vectorgraphics`,
但長年停留在 preview,一度懷疑已經不能用。

## 已確認的事實

### `com.unity.vectorgraphics` 其實還能用(2026-10-01,於 `Yu5h1LibTest` 實測)
用 MCP 連線的 Unity Editor 實際安裝 `com.unity.vectorgraphics@3.0.0-preview.7`,匯入一個含貝茲曲線的
測試 SVG:**編譯無錯誤,成功產生有效的 `Sprite` 資產**(`SpriteRect` 尺寸與路徑吻合)。結論:「長年
停滯在 preview」不等於「不能用」,它的 SVG 解析器目前仍可正常運作。測試完已移除套件與測試檔,專案
回到乾淨狀態。

### UI Toolkit 原生已經有向量圖形型別
`UnityEngine.UIElements.VectorImage` 是**引擎核心模組原生型別**(`UnityEngine.UIElementsModule`,不需要
裝任何套件),`Image.vectorImage`/USS `background-image` 原生支援渲染它。`com.unity.vectorgraphics` 的
匯入設定有 `svgType` 選項可以選匯出成 UI Toolkit 模式,直接產生 `VectorImage` 資產。

### HealthAI 的動態圖示完全不靠「烘焙 + 細分」,是每幀現場重算座標(2026-10-01,查 `SignalGraphic.cs` 全文 509 行)
這是最重要的發現,直接影響「動態圖示」該怎麼設計:

- **沒有頂點動畫系統,也沒有「細分版 vector 資料」**。每個圖示是一個 `private void XxxIcon()` 方法,
  裡面直接用 `painter.MoveTo`/`LineTo`/`BezierCurveTo`/`Arc` 描述路徑,`generateVisualContent += Draw`
  讓 UI Toolkit 在需要重繪時呼叫這個方法——**路徑座標本身就是程式碼算出來的,不是從任何資料讀出來的**。
- **基本 move/scale**:`Walker()` 走路圖示,四肢端點位置 `20 - stride * 0.4f` 這種直接用 `Clock`(時間)
  算出的偏移量,沒有特殊系統,UI Toolkit 的一般 style transform 就夠。
- **點動畫**:`Heart()` 心臟脈動——`Vector2 Point(float x, float y) => P(32 + ... + (x-32)*scale, ...)`,
  整顆心臟的**每一個貝茲曲線控制點**,每一幀都用同一個 `Point()` 函式重新算一次,圍繞中心 (32,32) 縮放,
  `scale` 由 `Mathf.Sin(Clock * ...)` 的心跳波形驅動。
- **區域變形**:`Ecg()` 心電圖波形——`for (int x = 4; x <= 60; x++)` 每個 x 取一個取樣點,依
  `Mathf.Repeat(x + phase, 64)` 落在波形的哪一段,用 `Mathf.Lerp` 算出對應的 y 值,`phase` 隨時間推進讓
  波形往左跑。**解析度就是這個 for 迴圈的取樣密度**,想更平滑就把步進改小——跟「vector 資料需要細分版」
  完全無關,因為這裡根本沒有預先存的 vector 資料。

**結論**:只要圖示是用程式碼描述(不是匯入的靜態 SVG/`VectorImage` 資產),`Painter2D` 的
immediate-mode API 本身就完整支援任意參數驅動的連續變形,UI Toolkit 這塊**不是缺口**,HealthAI 現有的
做法已經是這個問題的正確解法。

## 定案的分工

- **素材來源:SVG**,web 與 Unity 共用同一份原始檔,不維護兩套圖示系統。
- **`com.unity.vectorgraphics` 只在 Editor-time 用來解析 SVG**,烘焙成下列其中一種 runtime 格式;
  **runtime 完全不依賴這個套件**,即使它日後真的被棄用,已烘焙的 icon 不受影響。
- **路線 A(原生 `VectorImage`,優先)**:烘焙成引擎原生的 `VectorImage` 資產(`svgType` 選 UI Toolkit
  模式),直接給 `Image.vectorImage`/USS 用,支援 `tintColor` 簡單變色,也支援**有限幾種固定形狀之間
  切換**(例如麥克風待機/錄音兩態——烘焙成兩張不同的 `VectorImage`,依狀態切換引用哪一張,不需要自己
  寫渲染邏輯)。**沒有連續參數驅動變形需求的 icon 一律走這條。**
- **路線 B(自訂 `Painter2D`,比照 HealthAI 既有做法)**:只保留給真正需要**連續參數驅動**的形狀
  (像 `Heart()` 的心跳縮放、`Ecg()` 的波形),直接用程式碼描述路徑,不透過任何 vector 資料格式。
  **這條路線不需要額外的資料格式或子系統——程式碼本身就是完整方案**,跟當初設想的「`common` 存路徑
  指令的 SO」不同:那個 SO 格式適合「固定形狀、換個地方畫」,不適合「每幀都要用公式重算的連續動畫」。

## 待討論

- **要不要做一套「資料驅動的參數化動畫圖示」格式**,讓設計師不用寫程式碼就能做出像 `Heart()`/`Ecg()`
  那種連續動畫圖示?這是遠超過「匯入 SVG 當靜態圖示」的另一個量級的子系統(需要定義「哪些點、怎麼隨
  參數變化」的通用描述格式),目前**沒有任何消費端提出這個需求**,純粹是技術上的可能性討論,不是定案
  方向。在真的出現第二個需要連續動畫圖示的消費端之前,先不做——沿用「已有第二個使用者/第二份實作」
  才抽成通用元件的既有門檻([套件解耦計畫.md#禁止事項](file:///W:/UnityProject/HealthAI/docs/unity/套件解耦計畫.md#禁止事項))。
- Editor 烘焙工具(SVG → `VectorImage` 或路徑指令)要不要借用 `com.unity.vectorgraphics` 的 SVG
  解析器,還是自己寫一個範圍限定在「path 指令」的小解析器——尚未決定,待第一個真正要烘焙的 icon 出現
  時再排。
