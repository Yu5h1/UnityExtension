# 專案開發系統分析技能計畫

> Task ID: project-system-analysis

討論草案：從 UnityExtension 的實際開發需求出發，規劃一套讓 agent 在實作前分類需求、比對 Yu5h1Lib 能力並提出選案的技能。核心方向是「啟用技能 → 列出項目與匹配方案 → 定案」。技能細節與正式歸屬仍待收斂。

## 系統位置與關係

```text
專案開發工作流
├─ 專案需求與製作要求
│  └─ 功能、目標平台、現有依賴、編輯與微調方式
├─ 專案開發系統分析技能（規劃中）
│  ├─ 整理需求並依功能分類
│  ├─ 查找 Yu5h1Lib 技能、元件、Prefab 與案例
│  └─ 比較匹配方案、缺口與依據，形成定案材料
└─ 依定案製作與驗證
   ├─ 重用資產、填入資料、組合元件
   ├─ 補足必要的程式行為
   └─ 將使用經驗與能力缺口回饋給庫

共享規則／知識索引 → 未來的技能啟用入口（待定）
UnityExtension 能力指南 → 選案依據
Agent 文字工作流 → 選案後操作 Unity 的候選方式
```

與 [Agent friendly workflow](Agent%20friendly%20workflow%20Yu5h1Lib.UnityExtension.md) 的關係：本計畫整理「需求應採用哪些能力」；該草案繼續討論文字描述、類型註冊與 Unity 同步。能力選用流程可以先以既有文件與資產試行。

## 目標與開發方向

AI 能實作功能，但每次重新寫程式會錯過 Yu5h1Lib 已累積的組件與做法。分析技能應讓這些經驗在選案階段被找到，並說明何時適用、如何組合、哪些部分仍需補足。

優先考慮 data-driven 的製作方式：使用現成 Prefab 與元件，填入資料或調整配置即可完成需求。把「能在 Scene View／Inspector 預覽與微調，並保存調整」列入需求，而不只驗收執行後的功能。

程式負責必要的行為與動態生命週期。若把可預先編輯的物件結構、綁定及數值全部藏在 `Start()`，導致編輯時無法查看或調整，就需要重新評估交付方式。動態內容仍可在執行期建立，但應評估是否能沿用可編輯的 Prefab 模板。

選案以需求與證據為準；既有能力不匹配時，應具體列出原因與缺口，再決定擴充或新增實作。

## 候選分析流程

1. **整理需求。** 分類功能，同時記錄平台、現有技術、依賴與製作要求；例如原生 iOS 與 Unity iOS 應分開分析。
2. **比對庫能力。** 從需求用途查找 Yu5h1Lib 的技能與指南，再核對真實程式、Prefab、資料資產及使用案例，避免只靠類別名稱猜測。
3. **列出匹配方案。** 說明可直接重用、需要組合、需要擴充或需另行實作的部分，附適用條件、限制及待確認事項。
4. **定案。** 收斂各項需求的採用方案與理由，記入消費專案的設計文件；具體定案方式仍待討論。
5. **驗證與回流。** 檢查功能與可編輯性，把有效組合、錯誤用法、平台限制及新能力需求交回其權威文件。

方案定案後，局部修改沿用既有決策；需求或關鍵證據改變時才重新分析相關項目。

## 分析結果格式草案

以下是欄位示意。UI Toolkit、uGUI、ValuePort 及 TMP 相關 Prefab 都只是待核對的候選，沒有在本計畫確認其存在、支援範圍或相容性。

| 需求項目 | 製作與調整要求 | 候選方案 | 證據與缺口 | 建議／定案 |
|---|---|---|---|---|
| 圖形介面 | 編輯時可預覽與調整 | UI Toolkit；uGUI 與既有 Prefab | 現有資產、平台及依賴是否匹配 | 比較後選定 |
| MVVM 綁定 | 配置可保存，連接關係可檢查 | Yu5h1Lib ValuePort 相關能力；專案程式 | 實際套件、支援控制項及資料型別待查 | 重用或列出缺口 |
| 彈出視窗 | 換內容與外觀即可重用 | 既有視窗 Prefab，含使用者提及的 TMP 相關候選；新組合 | 資產位置、公開欄位與事件待查 | 優先驗證既有組合 |

介面技術、綁定能力、Prefab 與 agent 操作工具應分開表達。MCP 是操作途徑；「AI 寫程式」是實作方式，兩者本身都沒有回答採用哪項功能方案。備案只在有實際取捨時列出。

匹配資料至少要能追溯用途、實際入口、依賴、最小組合與驗證範圍。推薦程度與驗證程度分開記錄：未測過不等於不可用，長期未修改不等於過時，計畫中的 API 也不等於已交付。過時判斷需要替代方案、契約變更或不相容等具體依據。

## 知識與回饋的落點

分析方法由未來的技能擁有；庫能力與用法留在各自指南，選案結果留在消費專案，避免多處維護相同內容。

- 找不到能力：改善用途詞彙與入口路由。
- 找得到但不會組合：補最小案例、接線方式與選擇理由。
- 能力不足或平台失敗：記錄重現條件、影響與驗收要求，沿用跨專案 requirements 流程。
- 應用內出現可重用成果：保存實際案例，再評估是否回收到庫。

正式啟用入口的候選分工是：AgentsRule 維持通用流程，知識索引依任務條件路由，技能承載分析步驟。這裡先記錄設計方向；正式技能的共用範圍、位置，以及與既有分析／設計技能的分工仍待決定。

## 試行與驗證方向

先以少量真實需求手動走完分析，例如圖形介面、資料綁定與彈出視窗。檢查 agent 能否從需求找到正確入口、引用真實 API 或資產、辨識不匹配的方案，並交付可預覽、可調整與可保存的結果。

記錄需要人工提示或糾正的地方、是否重複實作既有功能，以及微調是否仍須修改初始化程式。依試行結果收斂欄位與流程，再編寫正式技能。

## 待討論決策

1. **啟用範圍與定案方式。** 新專案、功能規劃、架構變更各需要多深的分析？哪些選擇交由 agent 判斷，哪些需要使用者定案？
2. **技能歸屬與既有流程。** 通用分析方法與 UnityExtension 特有選案知識如何分工？與現有工作路由、模組設計技能如何銜接，正式技能放在哪裡？
3. **能力資料的最小形式。** 先補既有技能的用途索引與案例，還是需要獨立能力清單？如何讓消費專案在不知道類別名稱時也能找到入口？
4. **第一個真實案例。** 選哪個現有專案與需求驗證流程？Prefab、資料與可微調的範圍要達到什麼程度？
5. **格式與回流成本。** 哪些欄位每次必填，哪些按需展開？如何更新證據而不讓每次小修改都變成完整分析？
