# Agent friendly workflow Yu5h1Lib.UnityExtension

討論草案：整理 Yu5h1Lib 的開發經驗，探索以 Markdown 描述並同步 Unity 物件的工作流。以下格式與同步行為是待驗證提案，尚未實作或定案。

## 系統位置與關係

```text
Yu5h1Lib.UnityExtension
├─ 可重用的經驗
│  └─ 組件用途、組合範例、適用情境與驗證方式
└─ Agent 文字工作流
   ├─ Markdown：階層、組件設定、名稱引用與設計說明
   ├─ 類型註冊：公開可用類型、欄位、預設值與範例
   ├─ 解析與比較：檢查文件，列出預計變更
   └─ Unity 同步：更新指定 GameObject 階層
      └─ 原生 Hierarchy、Inspector、Scene View：預覽與人工調整

Agent 修改文件 → 檢查與差異 → Unity 套用 → 人與 Agent 檢視結果
TaskProgress 的文字／介面互動經驗 → 參考工作方式，另行評估程式重用
```

## 目標與出發點

物理形狀、永久變形與雲端世界紀錄另見 [可變形物理世界與世界資產](可變形物理世界與世界資產.md)。本文件繼續擁有 agent 操作及術語擴充。

AI 不會自動知道 Yu5h1Lib 累積的經驗。這些經驗需要轉成 agent 能找到、能操作、能驗證的材料，才能在每次開發時被使用。

這套工作流希望讓人與 agent 透過可讀文字討論物件排序、結構與佈置，再由 Unity 呈現實際結果。物件仍存在於熟悉的 GameObject 結構中，沿用原生編輯介面。

使用者提出以 `.md` 表示階層及組件數值，透過註冊映射物件類型，並以名稱綁定結構，避免 agent 必須逐個透過 MCP 操作物件。平台友善包含兩個層次：不同 agent 都能讀寫檔案；將來不同引擎可共用哪些描述，則需要另外驗證。

「標記語言最容易讓 agent 上手」目前是工作假設。值得測量的是修改步驟、錯誤修復與結果是否正確，而不是只比較副檔名。原型有助於辨識模組邊界；已知會變動的解析、同步及 Unity 操作仍可先分開，無須等整套系統完成才整理。

## 可用開源資源 / 類似功能

先尋找能直接採用的完整方案；若已滿足需求，就不自行開發。若只缺部分能力，優先評估擴充或薄層整合，最後才考慮自訂格式與同步系統。Markdown 是候選操作介面，不是採用既有資源的必要條件。

本地 TaskProgress 的能力文件記錄了 `.checklist` 的瀏覽器讀寫及原生編輯入口。這支持「文字與可操作介面共用資料」的方向，但 Unity 還涉及物件生命週期、引用、Prefab 與 Undo，不能直接假定 checklist 引擎已解決這些問題。

參考入口：[TaskProgress 能力說明](../../../TaskProgress/.agents/skills/taskprogress-capabilities/SKILL.md)。

| [ReactUnity](https://github.com/ReactUnity/core) | MIT 程式碼；React 直接渲染到 uGUI、UI Toolkit 與 Editor，使用 CSS／flexbox | 可參考宣告式更新；導入 React 及 JS 執行環境的成本較大，偏 UI 框架 |
| [Delight](https://github.com/delight-dev/Delight) | MIT；XML 描述可組合、可重用的 Unity UI | 參考文字元件與重用設計；需確認目前 Unity 相容性與編輯流程 |
| [Unity-Scene-Query](https://github.com/Real-Serious-Games/Unity-Scene-Query) | 用類 CSS selector 與階層路徑尋找 GameObject | 可參考名稱查詢；查詢本身不解決改名、同步或持久身分 |
| [dec](https://github.com/zorbathut/dec) | 面向 C# 遊戲的 XML 資料宣告，與引擎解耦 | 可參考類型與資料描述；其定位是資產定義，並非每個 Scene 物件實例 |

本次找到多個相近實作，尚未確認有專案完整涵蓋「Markdown、一般 Scene、名稱綁定、保留手動編輯、差異同步」這個組合。這是搜尋範圍內的結論，不代表不存在。

### 一般物件結構與骨架的候選資源

PromptUGUI 的公開定位是 UI，不能據此推定它能完整管理一般物件與骨架。研究範圍需擴及場景描述、模型交換及 Unity 原生資產，不能只比較 UI 框架。

| 資源 | 已有能力 | 可採用的部分 | 尚待查證的缺口 |
|---|---|---|---|
| [OpenUSD](https://github.com/PixarAnimationStudios/OpenUSD) | 通用場景描述、組合與資產引用，可使用文字形式 USDA | 一般場景結構與跨工具描述的候選基礎 | Unity 任意 MonoBehaviour、Prefab 語意、人工編輯往返與差異套用是否需另行整合 |
| [UsdSkel](https://openusd.org/release/api/_usd_skel__schemas.html) | 骨架拓樸、bind pose、動畫、蒙皮綁定；以 joint 名稱路徑表示關係 | 骨架資料已有標準，不應先發明另一套；名稱路徑亦可參考 | 不等於完整製作 rig；IK、控制器及 Unity 特有動畫設定需逐項評估 |
| [Unity USD SDK](https://github.com/Unity-Technologies/usd-unity-sdk) | Unity 與 USD 的既有整合入口；README 指出已被新 USD 套件組取代 | 沿官方替代路線評估，而非從零建立 USD importer | 現行套件相容版本、各 schema 支援、匯出與骨架往返能力，均須實測 |
| [glTF](https://github.com/KhronosGroup/glTF) ＋ [UnityGLTF](https://github.com/KhronosGroup/UnityGLTF) | 場景節點、模型、skin 與動畫的交換；UnityGLTF 提供匯入／匯出 | 若需求是帶骨架模型或物件階層的交換，可先試既有資產流程 | 不可把一般模型交換視為 Unity 任意組件的完整場景序列化；名稱也不取代 glTF 內部索引引用 |

以上是公開能力與待查證範圍的區分，尚未完成對本專案的採用驗證。標準支援某種資料，不代表某個 Unity importer 已完整支援，也不代表重新匯入會保留既有物件身分。

### 骨架與物件結構是否需要自行設計

「骨架」先涵蓋兩種可能需求，以免過早縮小問題：一般組合的基本階層，以及角色的骨骼／rig。兩者需以不同案例驗證。

| 需求層次 | 優先處理方式 | 可能需要自行補足的部分 |
|---|---|---|
| 空物件、父子關係、排序與 Transform | 評估既有場景描述或沿用 Unity Scene／Prefab，先測 agent 可讀介面 | 名稱解析、局部變更與操作回饋 |
| 既有 Prefab 與自訂組件的組合 | 先重用現有資產及 Yu5h1Lib 組件 | 類型註冊、可調欄位、引用映射 |
| 骨骼樹與掛點，例如手部掛武器 | 優先引用既有模型／骨架，定位指定 bone 或 socket | 名稱映射、掛點規約，以及保留原骨架的修改流程 |
| 蒙皮、bind pose、骨骼動畫 | 先驗證 glTF／USD 等既有格式與工具 | 匯入差異及 Unity 設定整合；不在 Markdown 重新手寫整批權重資料 |
| IK、rig 控制器、重定向或程序動畫 | 先盤點實際使用的 rig／動畫工具與元件 | 只描述那些工具公開且可驗證的參數與連接 |

目前無足夠證據斷言需要自製一套通用系統。比較合理的候選是：重用底層 Scene／Prefab／模型格式，視缺口增加 agent 可讀的操作層。若既有方案已涵蓋工作流，連這一層也可以省略。

### 採用、擴充或自製的判斷

以 UI、一般物件組合、帶骨架角色三個代表案例比較；每個案例需包含一次初次建立及一次後續修改。記錄名稱定位、組件引用、人工調整保留、重新載入、差異更新、錯誤回報、授權與維護成本。

- **直接採用：** 既有工具完整完成所需案例，且導入成本可接受。計畫轉為使用指南與經驗範例整理。
- **擴充／整合：** 場景或骨架底層已完整，只缺 agent 操作介面或 Yu5h1Lib 類型映射。只實作已確認的缺口。
- **自製：** 候選工具在必要案例上有具體失敗紀錄，而且擴充成本高於自行維護。先明確記錄缺失能力，再決定自製範圍。

僅因格式不是 Markdown，或專案名稱含 UI，不能判定其內部能力一定不可重用；同樣地，支援建立階層也不足以判定整個工作流已完整。

## 擴充性：既有元件與 Markup 術語

使用者已有自行組合的聊天面板及自製 UI 元件。評估重點包含如何沿用這些成果，而非要求全部改寫成候選框架的內建控制項。目前尚未定位及檢視這些實作；以下以聊天面板作為需求案例，不假定它現有的類型、功能或資產結構。

### 語法與詞彙分開評估

新增 `ChatPanel`、`MessageBubble` 等詞彙，理想上只需增加註冊、模板或元件轉接，不應每次修改核心解析器。父子關係、屬性、引用與事件的語法則維持一致。範例名稱只是討論用語，未指定最終 API。

| 擴充需求 | 優先方式 | 必須確認 |
|---|---|---|
| 既有元件換一組外觀或預設值 | 樣式、設定或模板 | 是否無須新建 C# 類型就能重用 |
| 多個元件組成聊天面板 | Prefab 或組合模板映射成一個術語 | 能否保留既有內部階層與組件引用，公開必要參數及插槽 |
| 自製繪製或互動元件 | 註冊標籤及 C# 轉接 | 是否必須繼承框架基底、重寫原元件，或修改套件原始碼 |
| 訊息列表、輸入狀態及送出事件 | 公開資料與事件連接 | 更新時是否保留輸入、捲動位置，且不重複訂閱事件 |
| 新增一般物件或骨架相關術語 | 使用同一註冊方式或明確的平台擴充 | 註冊機制是否被 UI 佈局與控制項生命週期綁死 |

### 每個術語要交付什麼

一個名稱能成功建立物件，只完成了部分擴充。還需要描述：

- **名稱與來源：** 所屬套件、版本、命名衝突處理；例如 `chat:Panel` 可作候選命名方式。
- **實際映射：** 對應既有 Prefab、組件或建立程序，以及需要的依賴。
- **公開屬性：** 型別、預設值、限制、可讀寫性與可接受引用；不必暴露全部內部欄位。
- **組合位置：** 哪些子節點由元件管理，哪些插槽可讓使用者放入自製輸入框、訊息樣式等內容。
- **資料與事件：** 可連接的資料來源、事件及參數型別；聊天服務與儲存邏輯仍由既有程式負責。
- **更新行為：** 哪些變更可原地套用、哪些需要重建；回寫能力與不支援的操作須可查詢。
- **Agent 使用資料：** 可列舉的術語清單、schema、簡短說明、正確範例與可定位錯誤。新增註冊後，這些資料應同步更新。

同一份註冊資訊應盡可能供建立、驗證與用法查詢使用，避免另養一份容易過時的標籤手冊。若更名或移除公開屬性，需回報舊文件不相容或提供遷移，不可靜默忽略。

### 開源方案已有的擴充入口

[PromptUGUI 的擴充說明](https://github.com/Heerozh/PromptUGUI/blob/main/BEST_PRACTICES.md) 已描述模板重用，以及自訂 `Control`、`[UIAttr]` 和 `UI.Registry.Register<T>(...)` 的註冊方式。因此，它的 UI 定位不等於不能新增自己的標籤。仍需用既有聊天面板驗證：能否僅以薄層接入、公開既有事件，以及保留其狀態；文件中的自訂 Control 範例不能證明任意既有元件可直接使用。

[Delight 的 Views 說明](https://delight-dev.github.io/Tutorials/Views.html) 涵蓋自訂 view、屬性、動作與 Unity 組件映射，亦是擴充性比較對象。採用前需衡量既有程式轉接到其 view／屬性模型的成本。

### 擴充性驗收

以既有聊天面板及一個自製 UI 元件作為採用評估的必要案例：接入元件、公開一個設定、接上一個既有事件，再更換一次內容或樣式。驗證核心 parser 無須修改、舊文件仍可使用、註冊後 agent 查得到正確用法；重複同步不增加事件訂閱，也不無故清除使用中的狀態。

若一般元件接入就必須 fork 框架或重寫大部分既有功能，應記錄為採用成本。只有明確的格式能力缺口才考慮修改語法；新增業務名稱通常應由詞彙註冊解決。

## Markdown 格式草案

先保留「階層與組件設定分開」的直覺。建議機器讀取區塊使用固定語法；一般 Markdown 段落作為說明。下例尚非可執行規格。

````markdown
# scene1

```scene-tree
a
  b
    c
    d
  e
```

```scene-values
/a:
  Transform:
    localPosition: [0, 0, 0]
/a/b/c:
  Transform:
    localPosition: [0, 1, 0]
```
````

階層以縮排表達父子關係，出現順序表達 sibling order。使用者提出的 `├─`／`└─` 樹狀線可作顯示形式；是否也接受為輸入，可由相同案例比較編輯成本。欄位區塊可採 YAML 子集，但須明確定義允許的型別及引用語法，不能只靠冒號讓 parser 猜測。

以完整名稱路徑區分不同父物件下的同名節點；同一父物件下重名先報錯。須定義名稱中的斜線、空白、大小寫及多個同型組件的表示方式。資產可公開可讀別名，由註冊表解析到 Unity 資產引用，避免 agent 手寫內部 ID。

先以單檔驗證。當一段內容已有獨立重用需求時才抽成 Prefab 或外部文件；拆分後需檢查缺失檔案、循環引用與相對路徑，不依檔案長度自動切割。

## 經驗如何轉成 Agent 可用材料

以一個已驗證組合為單位記錄：解決什麼問題、需要哪些組件、如何連接、哪些值適合調整、如何確認結果，以及何時應改用別種組合。範例應指向實際 Prefab 或可同步文件。

類型註冊應能產生或提供 agent 查詢的欄位說明與範例，減少手寫文件和程式分歧。格式負責描述結果；用途與選擇理由負責傳遞 Yu5h1 的經驗。兩者一起才構成工作流。

## 驗證順序

| 階段 | 產出 | 通過條件 |
|---|---|---|
| 0. 採用評估 | UI、一般物件、骨架及既有聊天面板／自製 UI 擴充案例的候選方案能力表 | 決定直接採用、擴充或自製；完整方案通過時即停止自製規劃 |
| 1. 對照實驗 | 用同一小案例比較 Markdown 草案與相近 XML 方案 | 記錄修改次數、工具呼叫、格式錯誤與人工修正，確認自訂格式的收益 |

採用與格式對照完成後，依 [文字結構同步 — 原型、驗收與遷移](文字結構同步.md#原型驗收與遷移) 推進同步驗證，再以本文件的擴充性案例檢查既有元件接入成本。

## 待討論決策

- **既有元件的擴充成本。** 定位聊天面板及自製 UI 實作後，依「擴充性：既有元件與 Markup 術語」驗證原樣重用、薄層轉接與框架改寫的差距，再選擇註冊方案。

- **既有方案的完整性與骨架範圍。** 依「可用開源資源 / 類似功能」的案例比較決定是否需要自製；先釐清骨架需求是基本階層、骨骼掛點，或含蒙皮／rig 編輯。此決策先於自訂語法與具體同步實作選型。

1. **第一個真實案例。** 建議挑選 Yu5h1 已熟悉且常需調整佈局的小型組合，以檢驗既有經驗能否被重用。
2. **Markdown 的必要收益。** 比較是否確實需要說明、階層與設定共存一份文件；若 XML 已滿足操作需求，Markdown 也可承載工作說明並引用 XML，而非一定重造語法。
