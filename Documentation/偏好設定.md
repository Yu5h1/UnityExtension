## UI 綁定層

> Task ID: bindable-adapter-factory

### 架構

```text
PlayerPrefs                      一個 KEY 存一整包 JSON
   ↕ ToJson / TryParseFromJson
DataView : IDataView             string→string，key 比對不分大小寫
   ↕ ReadFrom / WriteTo
IValuePort                       Core MVVM 契約，值一律字串
   ↑ Preferences.ResolvePort 三段解析
   ├─ 物件本身是 IValuePort          ValuePortBase 子類（ValuePort、OptionSet）、OptionSelector
   ├─ IAdapterShell.adapter          ToggleAddon 等 UI_Adapter 殼
   └─ AdapterFactory<Component>      原生控件無殼，執行期建純 C# Adapter
```

### 綁定流程

`Start` → `BindAll()`：解析全部 port → 補齊缺少的欄位 → `BindTo(current)`（內含把存檔寫回控件、訂閱變更、無條件觸發一次 `NotifyValueChanged()`）。2026-09-28（R1）從 `Awake` 改到 `Start`，原因見[設計決策](#設計決策)；`WriteToBindings()` 已併入每個 port 自己的 `BindTo`，不再是獨立步驟。

取值順序：每個欄位一律「存檔 → `defaultSetting` → 控件值」（I3，修正 E8）。有 `_source` 時，`defaultSetting` 的成員 key 由 SO 準備，見 [SO 設定來源](#so-設定來源d6)。沒有存檔時 `current` 複製 `defaultSetting`；已有存檔時，`current` 的 getter 在載入存檔、訂閱 `Changed` 之後，把存檔缺少、`defaultSetting` 有的欄位併入（此時寫入照常觸發存檔）。`BindAll` 補缺欄位時依同順序：先查 `defaultSetting`，查不到才取控件目前值。補上的值屬於一次變更，會立即寫進存檔。變更經 `DataView.Changed` → `_changed` 事件 → `SaveOnChanged` 時寫盤。順序本身是程式碼規則，由 csharp-core.md 擁有。

port map 為 per-instance `Dictionary<Object, IValuePort>`，壽命跟 Preferences 走；`UnbindAll` 清空，`OnDestroy` 呼叫它。

## 設計決策

- **key 來源為 GameObject 名字（B1）**：2026-05-06 使用者決定，便利優先，脆弱模式可接受，真遇到問題再加安全機制。已知脆弱：改名後舊 key 成孤兒；Unity 預設名（`Toggle`）重名互相覆寫；改名無編譯期提示；名字不含父層路徑，大場景碰撞機率上升。
- **原生控件無殼綁定**：Adapter 是純 C# 類別，由工廠在執行期產生，不要求在控件上加元件。`ToggleAddon` 等 MonoBehaviour 殼保留為方法擴充用途，與綁定是兩條獨立路徑。
- **自有元件不寫 Adapter**：Adapter 只給改不動的元件（`Toggle`、`Slider`）。`OptionSet` 等自有元件繼承 `ValuePortBase`，由 base 處理綁定，繼承者只覆寫字串值與 parser。
- **Selector 綁 index，值屬於 `OptionSet<T>`**：`OptionSelector` 只知道 int（事件是 `UnityEvent<int>`）；T 只有 `OptionSet<T>` 知道（事件是 `UnityEvent<T>`）。Selector 不讀取 OptionSet 的值。
- **`ValuePortBase` 不得宣告 `ChangedCallback`**：該名稱屬於 `UValuePort<T>` 的帶型別事件（`UnityAction<T>`），非泛型的字串層對不上。base 以 `NotifyValueChanged()` 觸發寫回；帶型別的元件保留自己的型別化事件，值變時另呼叫它。
- **`SelectableAdapter` 不依賴**：使用者判斷意義不大，可能淘汰；本功能不假設它存在。
- **補上的預設值即落盤**：第一次綁定補齊的欄位（來自 `defaultSetting` 或控件值）立刻寫進存檔。因此事後修改 `defaultSetting` 或場景值，只影響還沒有該欄位的存檔。維持此行為；「只存使用者改過的欄位」是較大的設計改動，未採用。
- **Editor 綁定入口與驗證（I1）**：`_bindings` 改用 `[TypeRestriction(typeof(Component), filter = typeof(ValuePortResolver))]` 驗證拖入的控件：`TypeRestrictionDrawer` 先交給巢狀 `TypeRestrictionDrawer.Filter` 中 `key` 為 `ValuePortResolver` 的實作 `PreferencesBindingFilter`（common Editor）解析／拒絕並標出重名，再做原本的型別檢查。先前曾另立 `PreferencesBindingAttribute`／`PreferencesBindingDrawer`，2026-09-28 收回 `TypeRestriction` 以維持同一種叫法；`filter` 只是 runtime 型別的 key，Filter 由 Editor 端以 `TypeCache` 認領，runtime 不引用 Editor 程式碼。`CONTEXT/Component/綁定選取的控件`（掛在任一 Component 上，僅在該物件有 `_bindings` 欄位時顯示）批次綁定目前選取的物件。兩者與 MCP 的 `execute_code` 共用同一個 public static API：`Yu5h1Lib.EditorExtension.PreferencesBindingUtility.BindSelected`（輸入 host 與控件、回傳逐項結果：`Bound`／`AlreadyBound`／`DuplicateName`／`Unbindable`）。可接受的判定沿用 `Yu5h1Lib.MVVM.ValuePortResolver.Resolve`——`Preferences.BindAll` 的 `ResolvePort` 也改呼叫它，避免執行期與編輯期各存一份判定邏輯。`CONTEXT/` 選單需要 `MenuCommand` 提供 context，MCP 的 `execute_menu_item` 無法帶入，因此 MCP 路徑直接呼叫 `BindSelected`，不經過選單。
- **BindAll 警告（I2）**：`ResolvePort` 回傳 null 時發 Warning，指名物件與元件型別；同一 host 內欄位名重複時發 Warning；欄位名等於「元件型別名稱」或「型別名稱 + " (n)"」（如 `Toggle`、`Toggle (1)`）時發較輕的提示（`.print()`，非 Warning）。不維護禁用名稱清單：造成覆寫的是重名，不是名稱本身。
- **逐欄位取值順序（I3）**：見上方「綁定流程」的取值順序段落。`UserDataView` 的舊存檔會因此補進 `defaultSetting` 有、存檔缺的欄位（Email、Name 等），已被使用者接受，見[已知問題](#已知問題) E8。
- **JSON 格式改用 entries（D1，2026-09-25 定案並完成）**：`ToJson()` 不再自己手動拆 `JsonUtility.ToJson(this)` 的輸出重組成扁平字串，直接回傳 `JsonUtility.ToJson(this)`（即 `{"_entries":[{"key":...,"value":...},...]}`），修正 E1、E2。`TryParseFromJson` 早就兩種格式都吃（先試 `JsonUtility.FromJson`，`json.Contains("entries")` 判斷成功與否，失敗才退回舊的扁平手動解析）——只有寫入端改了，讀取端本來就相容，舊存檔不用遷移就能繼續讀。**影響 `UserDataView`**：它依賴舊的扁平格式做字串處理，這個改動後 `Preferences.SaveToPlayerPrefs` 產出的新字串它可能解析不了；VCP 自己的遷移不在本套件範圍內，同一個「VCP 自己執行」原則見本文其他 VCP 相關項目（例如 E9）。
- **啟動套用改到 `Start`，且無條件通知（R1，2026-09-28 定案並完成）**：原本卡在兩個各自獨立的問題，一次踩到才發現要兩個都解——（1）Unity 原生控件（`Slider.value`、`Toggle.isOn`）的 setter 內部本來就會「新值等於現值就不觸發 `onValueChanged`」，`BindAll` 灌值時如果剛好跟場景值相同，消費端（例如接在 Slider 上的元件）就收不到通知；（2）即使強制無條件通知，`BindAll` 原本掛在 `Awake`，這個時間點某些消費端依賴的東西可能還沒準備好（VCP 案例：`AudioMixerProxy` 用到的 Mixer 相關狀態要晚一點才緒），同一個 frame 硬灌值會被消費端的初始化蓋掉或直接沒反應，即使先前試過手動延遲幾幀呼叫 `Invoke` 也只是繞過症狀。兩個問題的修法：`ValuePortAdapter.BindTo`／`ValuePortBase.BindTo` 現在在 `dataview.WriteTo(this)` 之後一律呼叫 `NotifyValueChanged()`（新增的抽象／虛擬方法，各 Adapter 自己直接呼叫原生事件，例如 `SliderAdapter`：`c.onValueChanged?.Invoke(c.value)`），不管值有沒有變都通知；同時 `Preferences.BindAll()` 的呼叫點從 `Awake`（經 `OnInitializing`）改成直接覆寫 `Start()`——Unity 保證同一個 frame 所有物件的 `Awake` 都跑完才會有任何 `Start`，這個時間點消費端該有的狀態都已經就緒，不需要手動延遲幀數。`WriteToBindings()` 這個獨立方法也一併拿掉，寫回動作併入每個 port 自己的 `BindTo`。
- **Dropdown 存文字而非索引（D3，2026-09-28 定案）**：跟 `OptionSelector` 的 index 慣例不同——`DropdownField.value`（UI Toolkit）本身就是字串、沒有對應的索引，若 uGUI 端改存 index，同一份存檔換到 UI Toolkit 就無法沿用同一套字串化規則。改文字後跟 `DropdownField.value`、`OptionSet` 的字串化一致，代價是選項文字改名會失聯（跟索引存法「改順序即錯位」的代價是同一類取捨，只是踩到的情境不同）。已實作（2026-09-28，見[實作步驟](#實作步驟d3d4皆已定案可開始)步驟 4）：`DropdownAdapter`／`TMP_DropdownAdapter`（原 `UI_DropDownOps`／`TMP_DropDownOps`，2026-09-29 改名）已有 `IValuePort`。`DropdownAddon`（MonoBehaviour 殼，跟綁定是兩條獨立路徑）不受影響。
- **UI Toolkit 綁定用 UIDocument 旁元件（D4，2026-09-28 定案）**：採[建議形狀](#建議形狀d4)——`com.yu5h1.uitoolkit` 新增掛在 `UIDocument` 旁的元件，`OnEnable` 掃描帶 `bindingPath` 的值元素、包成泛型 port、跑綁定三步驟，`OnDisable` 解綁；生命週期歸 `UIDocument` 擁有者。沒有採用「讓 `Preferences` 認得一物件多 port」——那會讓 `_bindings` 的資料形狀跟著改，衝擊既有 uGUI 路徑，`Preferences` 應該繼續不需要知道 UI Toolkit 存在。尚未實作：`common` 還沒有非泛型 `IPreferences` 介面，`com.yu5h1.uitoolkit` 還沒有任何偏好設定相關程式碼，見[實作步驟](#實作步驟d3d4皆已定案可開始)。
- **SO 作為設定來源（D6）**：見 [SO 設定來源](#so-設定來源d6)。
- 密碼、token 等秘密不進任何一層：PlayerPrefs 為明文。

## 風險待驗證

2026-05-07 實作完成時列出的驗收項目，原本未留下是否已驗證的紀錄；2026-09-25 於 `Yu5h1LibTest` 以 MCP 補驗證四項，結果併入各項狀態：

- **IL2CPP build 後，`[AdapterRegistration]` 反射註冊與 `[Preserve]` 建構子存活**：實際跑了一次，結果有一項待釐清的發現，**先擱置、之後再測**（2026-09-29，使用者要求停止本輪驗證）。

  機器一開始缺 IL2CPP 需要的 C++ 工具鏈（`Could not set up a toolchain for Architecture x64`，需要 Visual Studio 2019/2022 含 C++ 工作負載＋Windows SDK 10.0.19041.0 以上），使用者自行安裝後（Visual Studio Community 2026）重跑成功。驗證腳本：`PlayerPreferencesDemo.unity` 加一個暫時元件，`Start` 後檢查 `PlayerPreferences.current` 是否補齊 `Toggle`／`MasterVolume`／`MusicVolume`／`SfxVolume`／`Fullscreen`／`Vibration`／`ShowSubtitles`／`PlayerName`／`Dropdown (Legacy)`／`Dropdown` 十個欄位，並手動改一個值確認寫回 `PlayerPrefs`；結果寫進 `Application.persistentDataPath` 的文字檔，另外交叉比對 Unity 自己寫的 `Player.log`。

  結果：`Packages/UI`（`ToggleAdapter`、`SliderAdapter`、`InputFieldAdapter`、`DropdownAdapter`）在 IL2CPP 下全部正常，9/10 欄位正確、改值正確寫回。唯獨 `com.yu5h1.tmpextension` 的 `TMP_DropdownAdapter`（`Dropdown` 欄位）沒有被 `AdapterFactory` 解析出來——`Player.log` 直接印出 `AdapterFactory<Component>: no adapter registered for TMP_Dropdown.`，不是驗證腳本誤判。在 `Packages/Plugins/TMP/Runtime/link.xml` 加 `<assembly fullname="Yu5h1Lib.TMPEextension" preserve="all"/>` 試了兩次（含 `clean_build`）都沒用；把完全相同內容改放到 `Assets/_IL2CPPVerify/link.xml` 就立刻解決，`Player.log` 的警告消失，欄位正確補上。控制變因只有檔案位置，這個對照本身是乾淨的。

  **但這個發現本身還不算定案**：使用者過去在 mobile／Windows／Web 專案都沒遇過類似的 IL2CPP 反射失效，需要靠 link.xml 才能救回來，對「為何偏偏這裡需要」持保留態度——可能是這個特定測試專案（`Yu5h1LibTest`，套件用 `file:` 本機路徑引用、`com.yu5h1.tmpextension` 是臨時加進 manifest 的）的組態特例，不一定是通用結論。且「Unity 只掃描 `Assets/` 不掃描 `Packages/`」这一步本身也只有行為比對佐證，沒有讀到 Unity 內部原始碼或官方文件直接證實。在有更多資料前，**不要**把 link.xml（不論放套件裡或自動注入）當成已驗證的修法動手實作；`Packages/Plugins/TMP/Runtime/link.xml` 這份沒用的檔案已經移除，避免誤導。之後要重測可以直接沿用上面同一套腳本＋build 流程。
- **控件被 Destroy 後 port 仍在 map 內；`Unbind` 需走 Unity 的 `== null` 比較（已驗證，非問題，2026-09-25）**：實測確認 `_portMap`在控件 Destroy 後確實保留該筆項目（key 是「fake null」——`== null` 判 true，但字典查找走 `Equals`/`GetHashCode`，找得到、清不掉），直到下次 `UnbindAll()`／重新 `BindAll()`。但 `UnbindAll()`（含 Preferences host 自己 `OnDestroy` 時呼叫的那次）呼叫已 Destroy 控件的 `Unbind()` 不會丟例外：`ValuePortAdapter.Unbind()` 只操作 adapter 自己持有的 `UnityEvent` 欄位（`RemoveListener`），這是純 C# 受管理欄位，控件原生物件被摧毀後這個欄位仍可存取，不會觸發 `MissingReferenceException`。之後重新 `BindAll()` 也會透過 `_bindings` 本身的 `== null` 檢查正確跳過已銷毀的項目。結論：殘留項目只是暫時佔用字典空間，無功能性錯誤，不需要修。
- **同一 Toggle 同時被殼與工廠包裝時 listener 重複，寫入次數倍增（部分屬實，但「倍增」不成立，2026-09-25）**：實測把同一顆 Toggle 的原生元件（走工廠路徑）與其 `ToggleAddon` 殼（走殼路徑）都放進 `_bindings`，確認兩者各自解析出獨立的 adapter 實例，都掛上同一顆原生 `Toggle.onValueChanged`——這部分屬實，且會被 I2 的重名 Warning 抓到（兩者 `GetFieldName()` 相同）。但「寫入次數倍增」不成立：`DataView.ReadFrom` 在寫入前先比較新值是否等於現有值相同才跳過，兩個 listener 從同一顆 Toggle 讀到的值必然相同，第二個 listener 的寫入會被這個相等檢查短路，實測切一次 Toggle 只觸發一次 `changed` 事件／一次存檔，不是兩次。
- **同一 Toggle 放進兩個不同 Preferences，listener 各自獨立（已驗證，2026-09-25）**：建立一個臨時的第二個 `Preferences<T>` 子類型（測試用，已刪除），跟正式的 `PlayerPreferences` 同時綁同一顆 Toggle。確認兩者 `KEY` 不同、各自的 `current`／存檔完全independent；切換 Toggle 只會讓還在監聽的一方更新；對其中一方呼叫 `UnbindAll()` 後，它就不再反應，另一方不受影響。
- **重啟後控件顯示上次儲存值；既有實作 `IValuePort` 的 MonoBehaviour 仍能綁（已驗證，見既有紀錄）**：前者已在 [Recent Work](../handoff.md) 2026-09-25「preferences 驗證」那筆記錄裡確認（退出 Play 存檔仍在，下次 Play 還原全部欄位）；後者已在同日「ValuePort 綁定重構」那筆記錄裡確認（`OptionSet`／`ValuePort` 這類自身即 `IValuePort` 的 MonoBehaviour 寫回持久化，使用者於 Editor 驗證過）。不需要重測。
- **重複呼叫 `BindAll()` 而中間沒呼叫 `UnbindAll()`，同一控件會疊加 listener（2026-09-25 於 I1–I3 驗證時實測重現，非推導）**：`AdapterFactory<Component>.TryCreate` 每次都建新的 Adapter 包裝原生控件，`ValuePortAdapter.BindTo` 內部的 `Unbind()` 只會移除「這個 Adapter 實例自己」掛上去的 listener，移除不了上一次呼叫、另一個已被丟棄的 Adapter 實例掛在同一個原生 `UnityEvent` 上的 listener。連續呼叫多次 `BindAll()`（例如重新掃描已 Instantiate 的面板時，範圍與舊呼叫重疊）會讓同一控件的 `onValueChanged` 疊加多個 listener，結果是「多寫幾次但值相同」——不是資料錯誤，但每次控件變更都會多觸發幾次 `SaveToPlayerPrefs()`。目前沒有機制偵測或警告這件事；`BindAll()` 前先呼叫 `UnbindAll()` 可以緩解，但要求呼叫端自律。

## 弊端評估

- **無編輯期驗證**：已改善（I1）。`_bindings` 的 `PreferencesBindingFilter`（經 `TypeRestriction` 的 `filter`）在拖入當下就驗證是否可綁並標出重名；仍有缺口：CONTEXT 選單與 drawer 只擋得住透過它們寫入的項目，`SerializedProperty` 以外的路徑（例如日後直接改 `.prefab`／`.unity` 文字）不受影響。
- **註冊只能靠腳本**：已改善（I1）。Editor 內可用 `CONTEXT/Component/綁定選取的控件`；MCP 改呼叫 `PreferencesBindingUtility.BindSelected`，比先前的 SerializedObject 腳本短很多，但仍以場景路徑定址（Unity 6.3 的 `GetInstanceID()`／`InstanceIDToObject` 過時問題未變，見 [preferences skill](../.agents/skills/preferences.md#scene-procedure-mcp)）。
- **每次變動都寫盤**：Slider 拖曳時每幀 `PlayerPrefs.Save()`；WebGL 為同步寫 IndexedDB。
- **只在 `Start` 綁一次**：之後 Instantiate 的面板需手動 `BindAll()`。
- **綁定層消費端拿字串**：套用設定要自己 parse，無型別化讀取、無 Reset API。D6 以統一入口的 `Get<V>` 與恢復預設值處理，未實作。
- **單例一型一份**：兩組獨立設定需兩個子類別。
- **Selector 與 OptionSet 在同一物件時 key 相同**：兩者的欄位名都是 GameObject 名稱，同時放進 bindings 會互相覆寫，只能綁其中一個。
- **舊 key 不會清除**：控件改名、移除，或測試留下的欄位，會一直留在存檔裡，存檔只增不減（`Yu5h1LibTest` 的存檔裡仍有先前測試留下的 `sound`、`volume`、`choice`、`_DropdownField`）。不能在 `BindAll` 時自動刪除沒綁到的 key：同一個 host 型別的存檔由所有場景共用，這個場景沒綁到的 key 可能屬於別的場景。
- **沒有 key 命名空間**：同一個 host 底下，uGUI 和 UI Toolkit 共用同一組 key，只能靠手動加前綴區隔。撞名警告已於 2026-09-30 由[改善方向 7](#改善方向)補上（runtime `BindPort` 登記表＋`PreferencesBinder` Inspector），但仍沒有真正的命名空間。
- **兩套 key 身分機制**：uGUI 用 GameObject 名稱，UI Toolkit 用 `binding-path`，改名的影響和脆弱點各自不同（B1）。
- **只能綁控件**：`_bindings` 和 `BindPort` 都要求一個 `IValuePort`，沒有 UI 控件的欄位不能綁。**這不是缺口**：沒有 UI 的設定用 `ObservablePref<T>`，有 UI 才走 `Preferences`（P1 結案，見[待討論決策](#待討論決策)）。

## 改善方向

依成本由低到高，未排程。E3 警告與 E5 的 `print` 已於 2026-09-25 移除，E1／E2（JSON 格式改 entries，D1）與 Slider 的 `InvariantCulture` 已於同日完成，原第 1 項移除：

1. B1 其餘安全機制候選：可選的 key 覆寫欄位；改名時掃描受影響的 Preferences。重名檢查已併入 I2，觀察碰撞頻率再決定其餘。
2. 存檔節流：變動只標 dirty，於延遲或 `OnApplicationPause`／`OnApplicationQuit` 寫盤。
3. ~~補 Dropdown 的 `IValuePort`（D3）~~（已完成，2026-09-28，見[可綁控件](#可綁控件)與 UI Toolkit 實作步驟 4）。
4. `OptionGroup` 指定一個成員當 port：取值用 `member.TryGetItemText(群組 index)` 即可；設值需要 `OptionSet` 提供「字串 → index」的 API，因為 index 狀態在群組的 selector，成員通常沒有自己的 selector。
5. `PlayerPrefValue<T>`／`ObservableValue<T>`／`ObservablePref<T>` 代碼優化（2026-09-27 記錄，非移除理由，純打磨）：`PlayerPrefValue<T>.GetValue`／`SetValue` 每次直接讀寫 PlayerPrefs、`SetValue` 的相等比較也再讀一次，沒有快取；用 `typeof(T)` 分支＋boxing 轉型分派基本型別，可以考慮改用型別化的具體子類或原始碼產生器；key／預設值散落在各個序列化欄位，沒有集中登錄，重名不會被檢查；`PlayerPrefValue.Serializer` 是可被任何人改寫的全域靜態，同一份存檔的格式取決於執行順序，考慮改成 per-instance 或至少提供切換時的檢查。
6. 清理舊 key：Editor 指令列出存檔中沒有任何綁定、也不在 `defaultSetting` 的 key，由使用者確認後刪除。不做自動刪除，理由見[弊端評估](#弊端評估)。**已實作（2026-09-30）**：範圍只限該 host `KEY` 底下那一份存檔（`ObservablePref`、第三方套件各自的 PlayerPrefs key 不在範圍內）。消費者靠註冊機制收集——`PreferencesConsumerRegistry`（common Editor）內建 uGUI `_bindings`，UIToolkit Editor 註冊 UXML `binding-path`（common 不能反向引用 UIToolkit），以 `KEY` 相同判定同一份存檔。`PreferencesEditor<T>` 在 Inspector 以 foldout「Unclaimed List」（未認領，使用者定名）（縮排，展開狀態存 `SessionState`）列出沒有消費者的欄位——已載入場景有消費者的不顯示（使用者要求）；每列開頭一個燈號（使用者不要外框）：沒有消費者但在 `defaultSetting`＝黃燈（`defaultSetting` 當跨場景的登記，可能在沒開的場景用到）；兩者皆無＝紅燈，只有紅燈可刪：每列「x」或標題列 Refresh 右邊的「Clear」（刪全部紅燈），皆有確認對話框，Play Mode 停用；要刪黃燈得先從 `defaultSetting` 移除。`Preferences<T>` 是泛型，各實作自己宣告一行 Editor（`PlayerPreferencesEditor : PreferencesEditor<PlayerPreferences>`；VCP `UserDataView` 要用就自己加一行，其存法不同時覆寫 `WriteSave`）。讀存檔一律走 host 的 `TryLoadCurrent`。`PreferencesBinderEditor` 每個 `binding-path` 旁加上 saved／default 狀態，撞名判定也改走同一個註冊點。`IPreferences` 為此新增 `KEY`、`TryLoadCurrent`、`TryGetDefault`。MCP 實測（demo 場景，存檔先備份再還原）：uGUI 與 UXML 消費者都認得到，`sound`／`volume`／`choice`／`_DropdownField` 等測試殘留判為紅框，暫加進 `defaultSetting` 的 `sound` 判為黃框，刪除寫回與原字串一致。畫面經使用者確認（2026-09-30），改善方向 6 結案。

   **先釐清這個警告在防什麼**：一個值該只綁一個控件；「同一設定要在多個頁面出現」不是綁兩個獨立控件，而是（a）切頁面時搬同一個控件實例，或（b）另一頁做唯讀鏡像——直接讀 `current.TryGetValue`、訂閱 `changed`，不進 `_bindings`／不呼叫 `BindPort`，見[Consuming the values](../.agents/skills/preferences.md#consuming-the-values)。2026-09-29 MCP 實測證實現有系統沒有「兩個獨立控件即時互相同步」這回事：同一 key 綁兩顆 Slider，改動一顆，`current` 正確更新，但另一顆的畫面值不會跟著動，要等下一次 `BindAll()`。所以撞名永遠是意外，不是正當需求，警告不會誤傷合法情境。

   **現有缺口比「把 `seenFieldNames` 搬進 `BindPort`」複雜**：`BindAll` 的重名檢查（I2）用的 `_portMap` 是 `Dictionary<Object, IValuePort>`，以控件物件為 key；UI Toolkit 的 port 包的是 `VisualElement`，不是 `UnityEngine.Object`，進不了 `_portMap`，`Preferences` 完全不知道 UI Toolkit 綁了什麼。要讓兩條路徑共用一份判定，需要：

   1. `Preferences<T>` 新增一個**以欄位名為 key** 的登記表（例如 `Dictionary<string, IValuePort>`），兩條路徑的 port 都登記進同一份，不是以物件為 key。
   2. `BindPort(port)` 綁定前查這個表：查到、且不是同一個 port 實例（要能區分「重新綁定同一顆」跟「換一顆新的來搶同一個 key」），才印警告，訊息沿用 I2「will overwrite each other」的措辭。
   3. **對應的解綁一併缺**：`PreferencesBinder.OnDisable()` 現在直接呼叫 `port.Unbind()`，`Preferences` 不知情，登記表不會清掉。UI Toolkit 面板關掉重開會留下鬼影登記，下次重新綁定被誤判成撞名，變成假警報。需要新增 `Preferences.UnbindPort(port)`（同時進 `IPreferences`），把登記表裡屬於這個 port 的那筆移除；`PreferencesBinder.OnDisable` 改呼叫這個而不是直接叫 `port.Unbind()`（`UnbindPort` 內部再呼叫 `port.Unbind()`，呼叫端不用兩邊都呼叫）。

   `BindAll` 自己迴圈裡的 `seenFieldNames` 檢查可以之後拿掉，改成完全依賴 `BindPort` 這一份，避免兩處各自維護一份重名邏輯。

   **Editor 端如何呈現（不需要 Play Mode，2026-09-29 定形狀）**：`VisualTreeAsset.CloneTree()` 在 Edit Mode 可以直接呼叫（2026-09-28 驗證 `bindingPath` 時已用過這個方式，不需要進 Play）。靜態檢查：讀 `_bindings`（uGUI 欄位名）＋對同一個 host 底下每個 `PreferencesBinder` 引用的 `UIDocument.visualTreeAsset` 呼叫 `CloneTree()` 掃出所有 `bindingPath`（之後 P1 落地再併入它的綁定清單），三邊合併比對重複。`PreferencesBinder` 目前沒有 CustomEditor（純預設 Inspector，只顯示 `_preferences` 一個欄位），是兩層缺口，不只是缺警告：**連「目前偵測到哪些綁定」都看不到**——uGUI 有 `_bindings` 這個可見的序列化清單，UI Toolkit 完全沒有對應顯示，要看綁了什麼只能自己去翻 UXML。

   新增的 CustomEditor：每個掃到的 `bindingPath` 各畫一個 `TextField`；撞名的那幾個外框畫黃色（跟 Unity 原生的欄位驗證錯誤視覺同一種語言，不需要另外發明樣式）；`TextField` 本身**可編輯**，改名直接寫回該元素在 `.uxml` 裡的 `binding-path` 屬性——警告跟改名是同一個 UI，不是分開兩塊。這連帶把上一段「改名工具」的可行性問題從「要不要做」變成「這個 CustomEditor 的必要功能」：`binding-path` 存在 `.uxml` 資產的 XML 文字裡，不是場景／prefab 的序列化資料，沒有現成的公開 API 可以「改某個元素的某個屬性再存檔」，需要走 XML 文字層級操作或 UI Toolkit 內部 API；`CloneTree()` 產生的 instance 查不回它在 UXML 原始檔裡對應的節點，所以定位要另外想辦法（例如以 `name`／掃描順序比對原始 XML），動手前必須先確認可行。uGUI 端不需要這一塊：選到該 GameObject，Hierarchy／Inspector 原生就能直接改名字，不是缺口，這個 CustomEditor 只管 UI Toolkit 這一側。這個構想跟[改善方向](#改善方向) 1（B1 其餘安全機制：改名時掃描受影響的 Preferences）同一個範疇，之後合併考慮，不是這裡另開一個獨立項目。警告掛在 binder 元件本身，不需要進 Unity 自己的 UI Builder／UXML 編輯器插標記。不需要 `EnhanceCollectionField`：那個是 List／array 欄位的搜尋列與工具列強化（見 [Editor擴充.md](Editor擴充.md#enhancecollectionfield更新計畫)），跟重複偵測無關，偵測邏輯不依賴它。

   **寫回 `.uxml` 可行性（2026-09-30 以 MCP 於 Unity 6000.6.0f1 實測，結論：可行）**：

   - **清單從 XML 讀，不從 `CloneTree()` 讀**：原本擔心的「`CloneTree()` instance 查不回原始節點」在這個做法下不存在——CustomEditor 直接解析 `.uxml` 列出帶 `binding-path` 的元素，每一筆本來就是檔案裡的一個節點。實測 demo 檔 XML 解析出的清單與 `CloneTree()` 查到的完全一致（同順序、同型別、同值）。
   - **寫回必須只替換屬性值，不能整份 XML 存回**：`XDocument` 整份存回在乾淨檔案上 byte 相同，但遇到 CRLF、單引號、多餘空白時會全部正規化，`&#10;` 更會被展開成真的換行、改變 label 的實際值（實測）。改用 `XmlReader` 的 `IXmlLineInfo` 定位 `binding-path` 屬性所在的行和欄，回到原始文字只替換引號內的值（新值做 XML escape）：實測 CRLF、XML 宣告、單引號、`=` 兩側空白、註解（註解裡的同名 `binding-path` 不會被誤改）、`&#10;` 全部保留，diff 只有值本身，重新匯入後 `CloneTree()` 讀到新名字。
   - **Template 是真正要設計的地方**：`binding-path` 的有效值有兩個來源——Template 檔裡元素自己的屬性（所有 `Instance` 共用），或父檔 `<ui:AttributeOverrides element-name=… binding-path=…>` 覆寫（實測 6000.6 有效）。所以清單要跟著 `<ui:Template src>` 遞迴並套用 override，每筆記住「有效值定義在哪個檔案的哪個節點」。同一個 Template 放兩個 `Instance` 又沒有 override，天生就是撞名；改 Template 檔本身會連所有 Instance 一起改，解不了——要解得在父檔新增 `AttributeOverrides`（前提是 Template 裡那個元素有 `name`）。
   - **尚未處理**：檔案層級的修改不進 Unity Undo，靠版本控制還原；UI Builder 同時開著同一份檔案且有未存檔修改時，之後它存檔會蓋掉這裡的改名（未實測）。

## UI Toolkit 適用分析

**給 `com.yu5h1.uitoolkit` 實作用。common 不實作 UI Toolkit 端。**

### 為何現有路徑無法直接用

- UI Toolkit 控件是 `VisualElement`，不是 `UnityEngine.Object`：放不進 `_bindings`，也不在 `AdapterFactory<Component>` 的鍵空間。唯一的 Component `UIDocument` 對應多個控件，而 `ResolvePort` 是一物件一 port。
- `UIDocument` 每次 `OnEnable` 重建 `rootVisualElement`，元素參照失效；`Preferences` 只在 `Start` 綁一次。

### 可直接重用

`IValuePort`／`IDataView`（Core，引擎無關）、`DataView`、`Preferences` 的載入存檔與 `current`、綁定三步驟（補預設 → 寫回 → 監聽）。

### 有利條件

值控件皆實作 `INotifyValueChanged<T>`，一個泛型 port 即涵蓋 Toggle、Slider、SliderInt、TextField、DropdownField、EnumField 等。key 可取 `BindableElement.bindingPath`（UXML `binding-path`），脫離名字依賴，agent 只改 UXML 文字即可完成綁定。

### 建議形狀（D4）

`uitoolkit` 新增掛在 `UIDocument` 旁的元件：參照一個 Preferences，於 `OnEnable` 查詢帶 `bindingPath` 的值元素、包成泛型 port、跑綁定三步驟，`OnDisable` 解綁。生命週期歸 UIDocument 擁有者，`Preferences` 不需認識 UI Toolkit。

common 需提供：

1. 非泛型介面（例如 `IPreferences`）暴露 `current`，讓元件能以序列化欄位參照任一 `Preferences<T>`。
2. 把綁定三步驟抽成單一 port 的共用操作，兩條路徑共用，避免規則分岔。

### 需先驗證

- **`bindingPath` 在 runtime 可讀（已驗證，2026-09-28）**：UXML `binding-path` 屬性會直接寫進 `BindableElement.bindingPath`；MCP 實測 `VisualTreeAsset.CloneTree()` 與透過 `UIDocument.rootVisualElement` 兩條路徑都讀得到同一個值，不需要額外的 Runtime Data Binding 基礎設施。
- **各控件值的字串化須與 uGUI 版一致（2026-09-28 定出對應表）**：

  | UI Toolkit 控件 | 對應 uGUI Adapter | 格式要求 |
  |---|---|---|
  | `Toggle` | `ToggleAdapter` | 沿用：小寫 `"true"`／`"false"`，讀入不分大小寫，額外接受 `"1"`。 |
  | `Slider`／`SliderInt` | `SliderAdapter` | 沿用：寫入 `InvariantCulture`，讀入先試 `InvariantCulture` 再退回 `CurrentCulture`。 |
  | `TextField` | `InputFieldAdapter`／`TMP_InputFieldAdapter` | 沿用：原字串直通，不轉換。 |
  | `DropdownField` | `Dropdown`／`TMP_Dropdown`（尚無 `IValuePort`，見[改善方向](#改善方向)） | `DropdownField.value` 本身就是選項文字，與 D3（文字）天然一致；但 uGUI 端要先補上 `IValuePort`，兩邊才有共同格式可比對。 |
  | `EnumField` | 無（uGUI 目前沒有 Enum 控件的 Adapter） | **未決，非阻塞**：存名稱（`Enum.ToString()`：改順序不錯位、改名字才失聯）或底層值（`Convert.ToInt32`：相反取捨）。沒有既有格式要沿用，是獨立的新決策而非跨 UI 相容性問題——留到真的要做 `EnumField` port 時再定。 |

- 替代方案：Unity 6 runtime data binding 以 `DataView` 作 `dataSource`。值全為字串，非字串控件皆需 converter，字典路徑支援未確認；目前不建議。

## SO 設定來源（D6）

> 狀態：大部分定案，未實作；尚有 3 項見 [D6 待決定](#d6-待決定)。

### 情境

- `Yu5h1Lib.Animation` 有一份設定，用 SO 承載；它不一定有 UI 綁定。
- 執行期有設定面板（UI Toolkit）可以修改這些值，而且要常駐保存，這是需要 PlayerPrefs 的唯一理由。
- 在 Editor 裡改 SO 要能直接看到結果。Editor 的 PlayerPrefs 是開發者本機的資料，不影響 build 後的使用者。

### 已定案

- **SO 只是預設值**：執行期不寫入 SO，SO 也沒有執行期副本。執行期的值只在依 `KEY` 共用的 DataView（見下方統一的存取入口；`Preferences<T>.current` 就是它）。套件讀 SO 只會拿到預設值；要讀執行期的值，經 `Preferences.Get(KEY, key, SO 的值)`。
- **host 名稱維持 `Preferences<T>`**：它擁有存檔、預設值與載入時機，不只是綁定；改成 `PreferenceBinding` 會與 UI Toolkit 的 `PreferencesBinder` 混淆，且牽動 VCP 等既有消費者。`<T>` 是 host 自己（CRTP）：`SingletonBehaviour<T>` 依它決定唯一實例，子類別（VCP `UserDataView`）依它覆寫載入／存檔。host 不知道資料型別。
- **引用 SO 的欄位叫 `_source`，可以不指定**：不指定就是自由版本，行為與現行 `PlayerPreferences` 完全相同。
- **一個 host 只引用一個 SO**：每份設定一個 host 子類別（`class AnimationConfigPreferences : Preferences<AnimationConfigPreferences> { }`），各自一個 `KEY`、一份存檔。
- **SO 以 opt-in 介面接入**，介面巢狀在非泛型的 `Preferences` 靜態類別（`Preferences.ISource`）。不巢狀在 `Preferences<T>`：巢狀在泛型類別裡的型別會帶著外層的 `T`，每個 host 型別各一個，不能當共用標記。`Preferences` 與 `Preferences<T>` 並存，同 `DataView` 與 `DataView<TKey,TValue>`。不用現有的 `IPreferences`：那是 host 的契約（`KEY`、`current`、`BindPort`…）。不 opt-in 的 SO 拖不進來，避免引擎資產（如 URP Asset）被當成來源。
- **host 依 `_source` 準備 `defaultSetting` 的成員**：
  - 清單以 `_source` 的成員開頭，依欄位宣告順序，值取 `_source` 的值（缺少就新增，已有就改成 `_source` 的值）；`_source` 沒有的鬆散 key 保留，排在後面。
  - 成員可多不可少：鬆散 key 給 UI 用；`_source` 的成員不會從 `defaultSetting` 消失。
  - key = 欄位名稱（DataView 比對不分大小寫）；哪些欄位算成員見 [D6 待決定](#d6-待決定) 第 1 題。SO 的值經值轉換成字串存進 `defaultSetting`。
  - **時機**：在 `OnInitializing`（`BaseMonoBehaviour` 的 `Awake → Init(true) → OnInitializing()`），也能手動觸發（`Init()` 本來就是 public；Editor 可提供選單呼叫它）。Edit Mode 手動觸發會改到場景中序列化的 `defaultSetting`，要記錄 Undo 並標記 dirty。
- **統一的存取入口**：套件自己讀寫的資料與 `Preferences<T>` 一致。兩邊原本的儲存形狀不同：DataView 把整份序列化成一段 JSON 存在一個 `KEY` 底下；`PlayerPrefValue` 則是一值一 key、物件走 XML／JSON。
  - **儲存形狀只有一種**：一個 `KEY` 一份 DataView JSON。新程式碼不得用 `PlayerPrefValue` 存這些值。
  - **入口在非泛型的 `Preferences` 靜態類別**：以 `KEY` 登錄一份共用的記憶體 DataView（第一次存取時從 PlayerPrefs 載入），`Preferences<T>` 的 `current` 也改用同一份。host 與套件寫的是同一個物件，誰存檔都寫出同一份內容，不會互相覆蓋。
  - **套件的讀寫**：`Preferences.Get<V>(KEY, key, fallback)`／`Preferences.Set<V>(KEY, key, value)`，`V` 由呼叫端提供，經值轉換與字串互轉；DataView 本身仍只存字串。fallback 用套件自己 SO 的值。存檔中的字串轉不成 `V` 時回傳 fallback 並發 Warning。
  - **套件只讀寫 SO 成員的 key**：成員之外的 key 沒有任何消費者登記，Unclaimed List 會把它判成可刪的紅燈。
  - **`KEY` 的約定**：有 `_source` 的 host 的 `KEY` = `_source` 的型別名稱，套件用 `typeof(AnimationConfig).Name` 就能對上，不需要引用 host 子類別。既有的 host 補上 `_source` 時，`KEY` 從 host 型別名稱變成 SO 型別名稱，舊 `KEY` 底下的存檔不再被讀取（舊值作廢，或先手動搬移）。兩個 host 引用同一個 SO 型別時共用同一份資料。
  - 限制：套件寫入時，已綁定的 UI 不會更新（綁定在綁定當下之後是單向的）；設定面板開著時同時由程式碼改值，畫面會顯示舊值。
- **載入時機**：host 在場景中，`Start` 時綁定（維持現行）。不做場景載入前的自動載入（見 handoff 的 Ruled-out）。套件不等 host：第一次經統一入口讀取時，入口自己從 PlayerPrefs 載入該 `KEY`。
- **恢復預設值**：把 host 的 DataView 恢復成 `defaultSetting`。`defaultSetting` 有的 key 恢復；沒有預設值的 key 不動。成員 key 的預設值即 `_source` 對齊後的值。這也是「在 Editor 改 SO 要能直接看到結果」的做法：本機存檔已有的 key 會蓋過 SO 的新值，開發時恢復預設值即可。
- **不做「只存被寫入過的 key」**：維持「補上的預設值即落盤」。改版要讓玩家拿到新預設值時，用恢復預設值清掉玩家的選擇（代價：玩家改過的值也一併回到預設，使用者接受）。
- **不做 host 的 `Set`**：值的解析與寫入由各 binding 自己處理，DataView 一律是字串，host 不需要型別化寫入。程式碼的讀寫走統一入口的 `Preferences.Get<V>`／`Set<V>`，型別由呼叫端提供。
- **型別不一致以提示處理**：binding 的值型別與 `_source` 對應欄位的型別不一致時，Editor 把該綁定項目標紅並說明理由（「binding 型別 X 與 `_source` 欄位型別 Y 不一致」），執行期綁定時發 Warning。binding 的值型別取自 `ValuePortAdapter<T,TValue>` 的 `TValue`（`Toggle`＝bool、`Slider`＝float、`InputField`＝string…）與 `ValuePort` 的值種類；取不到型別的 port（如 `OptionSet` 系列）視為字串。
- **Inspector 不另外畫執行期的值**：需要時用 inline 的方式處理。
- 相關約定：
  - **值轉換統一由 `PlayerPrefsSerializer` 的基底處理**：新增公開的純轉換方法（值 ⇄ 字串）；原始值與 Unity 結構類型由基底固定格式、不可覆寫（序列化器是可替換的全域靜態，格式不得取決於執行順序）；其他物件交給子類別。浮點逗號分隔（Color 為 `r,g,b,a`）。讀取時先試新格式，失敗再交給物件路徑，以相容 VCP 既有的 `ObservablePref<Vector3>` 存檔。序列化器維持頂層類別，全域存取點移到它自身。準備 `defaultSetting` 時把 SO 的 Vector／Color 欄位轉成字串需要它。**需改 Core，尚待授權。**
  - **`ObservablePref`／`PlayerPrefValue<T>` 凍結**：不再新增功能，用途由統一入口（`Preferences.Get`／`Set`）承接。統一入口實作、VCP 遷移後刪除；在那之前照常可用。
  - 風險：成員準備以反射讀 SO 欄位，IL2CPP 下的存活性與[風險待驗證](#風險待驗證)的 IL2CPP 項同類，實作後一併驗證。
  - **存檔節流不屬於儲存實作**（[改善方向](#改善方向) 2）；歸 host 還是歸入口，隨 [D6 待決定](#d6-待決定) 第 3 題。

### D6 待決定

1. **`Preferences.ISource` 的內容與成員範圍**：建議 `ISource` 為空的標記介面；成員 = SO 類別（含其基底中 `ScriptableObject` 以下的部分）宣告的序列化欄位：public 或 `[SerializeField]`、非 static／readonly、無 `[NonSerialized]`。`ScriptableObject`／`UnityEngine.Object` 本身沒有符合條件的欄位，`name`、`hideFlags` 是屬性，不會混入。
2. **統一入口與覆寫存取的 host**：VCP `UserDataView` 覆寫 `TryLoadCurrent`／`SaveToPlayerPrefs`，以自己的格式存多組使用者；入口直接讀寫 `PlayerPrefs[KEY]` 的 JSON 會讓它失效。選項：(a) 入口提供依 `KEY` 註冊的載入／存檔擴充點（即儲存介面化，同步、讀／寫／刪，預設 PlayerPrefs），`Preferences<T>` 的 virtual 改為註冊到這裡；(b) 覆寫存取的 host 不走入口，維持現行，但其 `KEY` 不能被套件經入口使用。建議 (a)。
3. **存檔的責任**：建議歸入口。入口的 DataView 變更時由入口存檔（host 存在與否都一樣，不會因 host 也存檔而寫兩次）；host 的 `SaveOnChanged` 與存檔節流改為入口的設定，host 不再自己寫 PlayerPrefs。

### ValuePort 作為通用 binding

`ValuePort` 是不依賴 UI 控件的通用 binding：一個元件就是一個值，拖進 host 的 `_bindings` 即綁定，由程式碼或 Inspector 的 UnityEvent 改值。key 仍是 GameObject 名稱（可覆寫 `GetFieldName`），拖進 Preferences 時由 Inspector 提示重名與「不對應任何成員」，不另加 key 選擇欄位。

- **型別由序列化的值種類欄位決定，預設為字串**（與現行行為相同，既有的 `ValuePort` 不受影響）：`ValuePort` 存一個值種類（列舉，範圍等於值轉換固定支援的型別：原始值、Vector2／3／4、Vector2Int／3Int、Quaternion、Color、Rect、字串）。內部仍以字串存值，經值轉換讀寫：
  - 型別化讀寫 `Get<T>()`／`Set<T>(T)`；`T` 與值種類不符時發 Warning 並拒絕。
  - 給 UnityEvent 動態參數的型別化 `SetValue` overload（float、Vector3、Color…），同樣依值種類檢查。
  - Inspector 依值種類畫對應的欄位（Vector3 欄位、顏色選擇器…），不再是字串輸入框。
  - 綁在有 `_source` 的 host 下、key 對應到 SO 成員時，型別以成員為準：Inspector 顯示成員型別，值種類不符時提示。
  - 列舉型別名稱不得叫 `ValueType`（與 `System.ValueType` 同名），暫名 `ValueKind`。
  - 依賴值轉換，排在 Core 授權之後。
- **一個 key 只能有一個 binding**：維持現行的重名警告；port 之間不互相同步，綁定維持「綁定當下 DataView → port 寫一次，之後 port → DataView」的單向形狀。多處要讀同一個值時，經統一入口 `Preferences.Get` 讀取。
- **對外發變更事件 `UnityEvent<string> changed`**：與 `Toggle`／`InputField` 的 `onValueChanged` 同一定位，讓設計師往下游接線。
  - 放在 `ValuePort`，不放在 `ValuePortBase`：`OptionSet` 系列已有自己的型別化選取事件，放在基底會多一個重複的字串事件。基底的 `NotifyValueChanged()` 改為 virtual，`ValuePort` 覆寫為「先呼叫 base 寫回 DataView，再觸發 `changed`」。
  - 綁定當下也觸發一次（`BindTo` 本來就會呼叫 `NotifyValueChanged()`），與 R1「綁定時無條件通知」一致，下游在載入後就拿到值。
  - 不依賴值轉換，可先實作。型別化事件（值種類為 Vector3 時改顯示 `UnityEvent<Vector3>` 等）待值種類實作後再決定。

### 禁止事項

- opt-in 介面不得巢狀在 `Preferences<T>` 裡（會帶著外層 `T`，不是共用型別），也不得拿 host 的 `IPreferences` 當 SO 的 opt-in。
- SO 資料不得嵌 `ObservablePref`／`PlayerPrefValue`：同一個值會有兩套儲存、兩個預設值。
- 不另立列出成員的介面：SO 資料本身就是成員清單，第二份會漂移。
- 新程式碼不得用 `PlayerPrefValue` 存放屬於某個 `KEY` 的值：儲存形狀只有「一個 `KEY` 一份 DataView JSON」一種。
- 判斷 `_source` 是否指定一律用 Unity 的 `!=`，不得用 `??`／`?.`：未指定的序列化欄位在 Editor 是 fake null、在 build 是真 null。

## 待討論決策

### P1 序列化物件成員綁定（已結案，不實作）

**結案（2026-09-30，使用者定案）**：沒有 UI 的設定用 `ObservablePref<T>` 就夠——它本來就是宣告在任何類別上的欄位，改 `Value` 時自己寫進 PlayerPrefs、啟動時自己讀回，值自己觸發存取，沒有「誰來通知寫回」的問題。分工是：**有 UI 走 `Preferences`，沒有 UI 走 `ObservablePref<T>`**。以下「綁定元件＋物件參照＋成員路徑＋反射＋快照比對」的設計是為了「不改目標類別」而存在，使用者確認欄位本來就為持久化而宣告、可直接用專用型別，所以不做。也評估過新增一個把值寫進 `Preferences` 那份存檔的欄位型別（暫稱 `PreferenceField<T>`，實作 `IValuePort` 呼叫 `host.BindPort(this)`），唯一目的是讓無 UI 的值與 UI 設定同一份存檔、共用 `defaultSetting`；使用者表示不需要，不做。以下保留原分析作為紀錄。

需求（使用者 2026-09-29 提出）：綁定目前只對應控件，序列化物件的成員（例如某個元件或 ScriptableObject 上的 `useFeatureB` 欄位）無法綁定。使用者的構想是用 `ClassA.UseFeatureB` 這種名稱對應到類別與成員。

分析：

- **名稱格式適合當 key**：可讀，而且天然帶命名空間，順帶解決[弊端評估](#弊端評估)的命名空間缺口。
- **但不適合用來找值在哪裡**：
  - 只有類別名稱，不知道是哪個實例（同型別多個物件、場景物件或資產）。
  - 類別改名或換命名空間，key 會失效，執行期查找也會失敗，而且沒有編譯期提示。
  - 執行期用字串找型別和成員要靠反射，IL2CPP 下有被裁切的風險（同[風險待驗證](#風險待驗證)的 IL2CPP 項）。
- **建議把兩件事分開**：綁定項目 = 物件參照（拖入元件或資產）＋成員路徑（Editor 下拉選取，存成字串）＋ key。key 預設產生為 `類別.成員`，但存成欄位，之後類別改名不會改到 key。
- **最難的是寫回來源**：一般欄位沒有變更事件，和 E4 的 `DataViewBinding` 是同一個根本問題。選項：
  - （a）只載入，存檔由呼叫端明確觸發。
  - （b）成員限定為 `ObservableValue<T>` 或有變更事件的屬性。
  - （c）在存檔時機（`OnApplicationPause`／`OnApplicationQuit`，或改善方向 2 的節流點）比對快照後寫回。不需要改目標類別，建議採用。
- **放置形狀**：沿用 D4 的理由，不改 `_bindings` 的資料形狀，另做一個綁定元件（類似 UI Toolkit 的 `PreferencesBinder`），把每個成員包成 `IValuePort` 後呼叫 `BindPort`，`Preferences` 不需要改。**跟[改善方向 7](#改善方向)的關聯**：這代表 P1 的綁定元件會是第三個直接呼叫 `BindPort` 的入口（uGUI 的 `BindAll`、UI Toolkit 的 `PreferencesBinder` 之後）。P1 預設 key 格式（`類別.成員`）天然帶命名空間、降低撞名機率，但不是偵測撞名——使用者自訂 key，或不同類別剛好撞到同一個簡短 key，一樣需要警告接住。改善方向 7 沒先做，P1 綁定會跟 uGUI／UI Toolkit 一樣，撞名完全不會警告；改善方向 7 做完，P1 不管做成什麼形狀，只要走 `BindPort` 就自動繼承保護，不用另外補判定。**因此改善方向 7 排在 P1 實作前面**。
- **值格式**：P1 屬於 UI 綁定層，值最後是 `DataView` 裡的一個字串，由 port 自己決定格式，和 `PlayerPrefValue` 的 `IPlayerPrefsSerializer` 無關（兩層儲存方式不同，見[成員總覽](#成員總覽)）。基本型別沿用[可綁控件](#可綁控件)的字串規則，列舉存名稱。複雜型別用 `JsonUtility.ToJson(object)`／`FromJson(string, Type)`：成員型別要到執行期才知道，非泛型版本剛好適用。`JsonUtility` 不支援頂層的原始值與集合（同 [E10](#已知問題) 的原因），這類成員要包一層物件或另外處理。
- **和現有層重疊**：程式碼擁有的欄位要持久化，現在已經有 `ObservablePref<T>`（見[成員總覽](#成員總覽)）。P1 多出來的價值是：不改目標類別、在場景裡設定、和 UI 控件存進同一份存檔並共用 `defaultSetting`。如果這些不是必要的，`ObservablePref<T>` 就夠了。

- 是否接受用「物件參照＋成員路徑」找值，類別名稱只當預設 key。
