# 可變形物理世界與世界資產

討論草案。探索讓遊戲世界由物件的生成方式、性質與互動持續形成，降低每種內容都必須先在 3D 編輯器中精工製作完成的依賴。可變形與保存是其中的具體需求；格式、演算法及實作路線尚未定案。

## 系統位置與關係

```text
Yu5h1Lib.UnityExtension
└─ 可變形物理世界
   ├─ 類型與生成配方：人、劍、地形
   ├─ 世界紀錄：來源、個體參數、永久修改與版本
   ├─ 物理互動：粒子、約束與材料狀態
   │  └─ Unified Solver 經歷：供回顧與比較，後端尚未選定
   ├─ 形狀更新：變形、斷裂、體積增減與表面重建
   └─ 可見與可碰撞結果：Mesh、材質、碰撞表示與細節層級

Agent markup → 編寫配方及操作 → 世界紀錄
本機／雲端保存 ↔ 世界紀錄 → 重建物理及可見結果
```

本文擁有世界資產與永久變形的探索。[Agent 工作流](Agent%20friendly%20workflow%20Yu5h1Lib.UnityExtension.md) 擁有文字操作與術語擴充；既有 [PhysicsParticle 計畫](../Packages/Unified-Solver/Documentation/Plan/PhysicsParticle.md) 擁有已定案的 layout／interaction／appearance 分工與後端中立方向，本文不改寫該契約。

## 出發點：世界如何形成

使用者在 [Unified-Solver](../Packages/Unified-Solver) 探索魚、彈跳、物理互動及群體行為時，開始質疑遊戲內容的生產前提：是否每種物件都必須先透過 3D 編輯器，耗費大量時間建模與調整，成為完成的數位資產後，才有資格進入世界？

這段經歷尚未收斂成答案。它提供問題、嘗試與觀察，不代表本計畫應延續該套件架構，也不代表粒子已被選為所有內容的最終表示。

「FBX」在這個討論中指向這種預先製作完成的資產工作方式，而非特定副檔名。只把 FBX 換成另一個檔案格式，或只將建模步驟搬進程式，仍未必減少內容製作的負擔。

希望探索的是：作者描述物件如何形成、具有什麼性質、能做什麼，以及如何與環境互動；系統據此形成個體，世界運行再持續改變它們。形狀、動作、互動與群體結果需要一起思考，不能把願景縮小為動態改 Mesh。

人工製作的資產仍可作為起點、細節或藝術指導。需要驗證的收益是：新增一種物件或變體時，有多少成果能由既有規則重用，有多少仍須逐件製作。參數化若只是把每件建模工作換成每件客製程式，也沒有達到預期。

## 想要得到的世界

物件從程序配方或預製形狀開始，之後真正受互動改變。打鐵留下凹痕與形變，斷劍形成新的斷面與分離物體，地形挖洞後留下可再次進入的空間。重新登入後，結果仍存在並影響碰撞及後續加工。

人可由「人這個類型＋五官比例、骨骼比例、外觀參數」建立。同一份類型定義產生很多個體，世界儘量保存可重建結果的資料，不要求每個個體各有一份 FBX。

## FBX 問題的技術補充

FBX 是資產交換途徑，並非 Unity 物件存在的必要條件。[Unity Mesh API](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Mesh.html) 可在程式中建立及修改頂點、三角形等資料，可以直接使用程序生成或其他形狀來源。

但不用 FBX 不等於能永久變形：匯入模型也能作可變形物件的初始資料；程序模型若缺乏更新與保存機制，仍是固定形狀。需要選擇的是世界的權威資料與更新方式，不必先禁止某種輸入格式。

## 形狀資產如何收斂

候選方向是一份物件配方產生初始表面、內部粒子與外觀綁定，減少重複編寫。相關資料仍有不同責任：

| 資料 | 作用 |
|---|---|
| 形狀配方 | 人的比例、劍的截面與長度、初始體積與細節 |
| 物理佈局與關係 | 粒子位置、約束與連通性，決定彎曲、保持體積及分離 |
| 外觀綁定 | 用蒙皮、控制籠、粒子權重或體積表面生成，將模擬變成可見形狀 |
| 材料行為 | 彈性、塑性、損傷等；與視覺材質分開 |
| 永久修改 | 與初始形狀的差異，例如塑性狀態、斷裂關係及挖除區塊 |

粒子可以作變形控制點，使某些物件不需要傳統骨架；但精細角色動畫或遠景表現也可能保留骨架更合適。共同生成來源不代表物理取樣與可見表面必須使用相同解析度。

五官及骨骼比例只能重建生成器能表達的形狀。任意凹痕、裂口、洞口通常超出這個參數空間，需要保存額外狀態。seed 也只有在生成器及版本一致時才足以重現初始結果。「材質 scale」需釐清是紋理比例、外觀參數，還是物理材料性質。

## 世界紀錄的候選內容

```text
物件紀錄
├─ 類型、配方版本、初始資產／生成器引用
├─ 初始參數及 seed（若使用隨機生成）
├─ 當前位置、歸屬及物件關係
├─ 永久形狀／材料修改，或快照引用
└─ 必要續算狀態：速度、塑性、損傷等
```

保存外形與精確續算要求不同。只存粒子位置可能遺失 rest configuration、材料歷史及約束狀態，下一步就回彈成舊形狀。應按物理模型定義保存契約，不能將 GPU buffer layout 直接當永久世界格式。

編寫時可使用名稱；持久化內部仍需評估不隨改名變動的物件身分與修訂版本，由系統管理而不必成為 agent 日常操作的 ID。

## 三種變化分別驗證

| 情境 | 必須發生的變化 | 單純移動粒子仍缺什麼 |
|---|---|---|
| 打鐵 | 卸力後仍保留變形，可繼續加工 | 塑性／永久參考形狀更新；精確鍛造另涉及溫度與材料模型 |
| 斷劍 | 兩部分獨立運動，形成斷面 | 物理連通性拆分、表面拓樸、切面、質量與碰撞更新 |
| 地形破壞 | 移除體積，形成洞穴或懸垂 | 內外部表示、區塊與表面重建、碰撞及局部保存 |

只在 shader 改變外觀不算完整驗收；畫面、碰撞及存檔要對應同一次修改。刪除粒子也不會自動讓三角形斷開或封口。

## Unified Solver 的已有基礎與限制

以下是先前探索可供參考的局部能力，不是本世界系統已收斂的基礎架構。

[Unified Particle Physics 論文](https://mmacklin.com/uppfrta_preprint.pdf) 提供不同物理互動共用粒子及約束框架的研究基礎，但不保證所有材料、解析度及硬體下都比其他方法快或精確。

本地 [SolverRenderProfile](../Packages/Unified-Solver/Runtime/Profiles/SolverRenderProfile.cs) 已允許剛體路徑從粒子凸包產生外形；[SolverMeshRenderer](../Packages/Unified-Solver/Runtime/Rendering/SolverMeshRenderer.cs) 的剛體模板網格在建立時生成。這是不用外部 mesh 資產的既有基礎，尚不能視為即時斷裂或永久變形已完成。

凸包會填平凹陷與洞口，不能單獨承擔打鐵凹痕及地形洞穴。稀疏粒子適合控制大尺度運動，不會憑空提供細緻表面。

依 [Unified Solver 操作知識](../.agents/skills/unified-solver.md)，部分擴充 kernel 由一個 thread 串行處理整個實體，增加到大量粒子需重新評估粒度；剛體路徑亦有同步 GPU 讀回成本。須量測求解、表面重建、碰撞更新與保存讀回的總成本。

PhysicsParticle 是已定案但未授權實作的方向。永久靜止形狀改變及實體分裂可能擴大其生命週期契約；須另外評估，不能假定初次生成 API 已涵蓋動態拓樸。

## 可用開源資源 / 類似功能

2026-09-07 查閱公開文件，未安裝、整合或測試。先採用已有能力，只為已證實缺口開發。

| 資源 | 可借用能力 | 邊界 |
|---|---|---|
| [PositionBasedDynamics](https://github.com/InteractiveComputerGraphics/PositionBasedDynamics) | PBD／XPBD、剛體與可變形體約束、細緻表面綁定 | 不是目前 Unity GPU solver 的直接替代或完整持久世界 |
| [Taichi Elements](https://github.com/taichi-dev/taichi_elements) | 多材料 MPM 研究及實作參考 | 粒子／背景網格流程不同；Unity 整合與即時成本待測 |
| [OpenVDB](https://www.openvdb.org/documentation/doxygen/overview.html) | 稀疏體積、level set 等操作，供地形及形狀保存參考 | 不是 Unity 即時物理框架 |
| [geometry3Sharp](https://github.com/gradientspace/geometry3Sharp) | C# 動態網格、重網格及隱式表面工具 | 幾何操作不等於材料破壞求解，需量測執行成本 |

固定拓樸網格可先驗證凹痕；動態網格須處理裂面；體積／SDF 可描述挖除，但薄片、銳邊及高解析度有成本；粒子／材料點通常仍需表面表示。這些可共存，不預設一種表示通吃角色、鍛造及地形。

## 雲端保存

先證明本機「修改、保存、關閉、載入、繼續互動」，再接雲端。小型參數可引用較大的形狀差異及區塊快照，不必把每顆粒子或頂點寫進 Markdown。

只存敲擊命令不保證跨 GPU、solver 版本及時間步長重播一致。候選為階段快照加有限操作歷史，並記錄生成器、schema 及演算法版本。

若多人同時修改，另需結果決定權、衝突處理及分裂後歸屬；雲端檔案儲存不自動解決這些問題。服務供應商暫不選定。

## 最小驗證順序

以下是先前提出的技術候選順序，尚未選定。應先從魚、彈跳、物理互動與群體行為的經歷，整理哪些內容必須手工製作、哪些已能由規則形成，確認真正想消除的重複工作，再選擇原型；不以鐵條變形預先限定整個願景。

1. **程序鐵條＋永久凹痕＋本機保存。** 卸力後保留形狀，重載後外形、碰撞及後續互動一致；先不要求精確熱鍛造。
2. **鐵條斷成兩段。** 驗證連通性、切面與碰撞，重載後仍可分別互動，不以預製斷劍替換。
3. **地形區塊挖洞。** 驗證洞穴、區塊邊界、表面及局部保存，測試是否需要不同表示。
4. **參數化角色。** 驗證比例可表達範圍及仍需的表面／綁定資料，不以鐵條成功推定角色也成立。
5. **雲端往返與版本升級。** 測量保存大小、載入時間及修改頻率，再決定多人範圍。

硬體、幀率、精度、物件數及世界規模尚待選定；性能包含整條更新與保存流程，不承諾未測量的提升。

## 待討論決策

- 哪一種內容最能驗證「降低逐件精工製作資產的依賴」？從魚及群體互動的原有經歷辨識具體製作負擔，再決定原型。

- 第一個案例選程序鐵條永久變形，或優先地形破壞？兩者可能導向不同表示。
- 物理程度是可控可信的互動，還是包含溫度、塑性與斷裂材料校準？
- 角色「材質 scale」具體指什麼，哪些細節須由參數生成？
- 保存恢復外形即可，或需在運動途中準確續算？雲端先單人或多人？
- PhysicsParticle 如何承接永久 rest state 變化及實體分裂？先驗證，再討論契約擴充。
