# UnityExtension 開發日誌

## 2026-09-16 — 指標手勢的擁有者

### 嘗試

把 HealthAI 的指標互動抽成套件後，在 Yu5h1LibTest 寫一個 Apps Menu 消費端驗收手感。
抽取本身逐行比對過來源，但消費端的事件接線是即興寫的。

### 結果

連續五輪互動失效，全部出在消費端的接線，套件本身沒有改過一行。其中四輪是同一個錯誤：
把「捕獲指標」和「跑手勢計時器」分給了不同元素。

失效方式都是靜默的 —— 不編譯錯、不丟例外。捕獲在別處時長按對移動盲目，拖到一半自己發動；
放手處理在別處時，元素一被面板隱藏，指標就永久卡住，之後所有點擊與拖曳全部無反應。

第五輪是在 flex 容器裡對拖曳對象 `BringToFront()`：子項順序就是排版順序，
拖第一格會把它變成最後一格，其他全部往前擠。

HealthAI 的三個呼叫點（角色舞台、顏色選擇器、桌面群組拖曳）都遵守同一條規則，
所以那邊一直是好的。差別不在它們用了不同做法，而在我讀它時只讀了「該搬什麼」，
沒讀「它怎麼接」。

### 決策

**手勢屬於哪個元素，那個元素就同時捕獲指標、跑自己的計時器。** 推論見
[指標互動與世界橋接](指標互動與世界橋接.md#一條規則管所有手勢)。

消費端範例改為與套件同行：`Packages/UIToolkit/Samples~/AppsMenu`。
它先前住在測試專案裡，而那個專案沒有版本控制。


## 2026-07-27 — Particle System 物理碰撞互動

### 嘗試

為 Unity `ParticleSystem` 製作 `ParticleSystemRigidbody` 元件，透過 `IJobParticleSystem` 在 CPU 端加入粒子彼此之間的球形碰撞、重疊修正、反彈與摩擦。

### 結果

Particle System 的 C# Job 操作仍在 CPU 執行。粒子碰撞需要同時讀寫碰撞雙方，限制了直接平行化；大量粒子或密集堆積時，碰撞配對與反覆求解的成本也會快速增加。

實際結果在碰撞穩定度、堆積效果與執行效能上都未達需求，因此不再繼續擴充 `ParticleSystemRigidbody`，相關實作已從 UnityExtension 移除。

### 決策

大量物件的碰撞、堆積與容器互動改由 `unified-solver` 處理，不再以 Unity Particle System 的 CPU Job 路線實作。
